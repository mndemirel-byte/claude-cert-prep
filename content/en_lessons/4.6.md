## The Core Idea

If a model reviews its own output in its own session, it carries its original context and is likely to miss the same mistakes. The fix: **an independent instance re-reviews without the earlier context.**

This resembles the "reviewing your own code" problem in software development — a human doesn't do that well either.

---

## The Limitation of Self-Review

### Scenario

A model analysed a complex invoice document and extracted 8 line items. Now the same model is asked to verify its own extraction.

### Why It Fails

```
When the model looks at its own analysis:
- The context it used while producing the original is still active
- The tendency "I made this interpretation, it looked reasonable then"
- Its own logic errors look natural — because it produced them with that logic
- Information it missed can be missed again — attention goes to the same places

Result: a high chance of skipping subtle errors when reviewing its own output
```

### Fix: An Independent Instance

```
Instance A → analyses the document → extraction X
Instance B → reviews the document INDEPENDENTLY (without seeing X)
           OR
Instance B → sees the document + X but in its own session, without A's context

Difference: B is more likely to catch the inconsistencies A missed
```

## Multi-Pass Architecture

You're analysing a large codebase. What happens if you hand over all files in a single pass?

### The Single-Pass Problem

```
Problem: attention dilution
- 50 files given at once
- The model pays more attention to early files
- Late files get superficial analysis
- Contradictory findings (X safe in file A, X dangerous in file B) may go unnoticed
```

### The Multi-Pass Fix

```
Stage 1: per-file local analysis
  - Each file is analysed separately
  - Consistent depth guaranteed — every file gets full attention
  - Output: per-file findings

Stage 2: cross-file integration pass
  - A separate instance sees all file findings
  - Detects data-flow problems (is data sanitised in A still clean in B?)
  - Flags contradictory findings
  - Catches system-level patterns
```

```python
def multi_pass_review(files: dict) -> dict:

    # Stage 1: per-file local analysis
    file_findings = {}
    for filename, content in files.items():
        findings = analyze_file(filename, content)  # Separate instance
        file_findings[filename] = findings

    # Stage 2: cross-file integration
    integration_findings = cross_file_analysis(file_findings)  # Separate instance

    return {
        "per_file": file_findings,
        "cross_file": integration_findings,
        "total_findings": merge_and_deduplicate(file_findings, integration_findings)
    }
```

## Confidence-Based Routing

Not all findings are equal. Some are clear, some ambiguous.

### Structure

Ask the model to report its confidence for each finding:

```json
{
  "finding_id": "SEC-003",
  "description": "Potential authentication bypass",
  "severity": "critical",
  "confidence": "low",
  "confidence_reason": "Code is complex; context is missing for a full analysis of the auth logic",
  "recommendation": "Security expert review required"
}
```

### Routing Logic

```python
def route_findings(findings: list) -> dict:
    auto_approve = []
    human_review = []

    for finding in findings:
        if finding["confidence"] == "high":
            auto_approve.append(finding)  # Continue in the pipeline
        elif finding["confidence"] in ["medium", "low"]:
            human_review.append(finding)   # Human review queue

    return {
        "automated": auto_approve,
        "human_review": human_review
    }
```

### Calibrating the Confidence Threshold

```
How to calibrate?
1. Build a labelled validation set (100 findings reviewed by a security expert)
2. Compare the model's confidence levels with the real outcomes
3. Find the optimal threshold: "medium" confidence → X% error rate

Result: confidence thresholds rest on concrete error rates — not intuition
```

## Contradictory Findings — Same Code, Different Instance Decisions

```
Instance A: auth.py → "no rate limiting, critical"
Instance B (cross-file pass): rate limiting seen in middleware.py
→ the auth.py finding: false alarm, or can the middleware be bypassed?

This contradiction is flagged automatically:
{
  "conflict_detected": true,
  "finding_a": "auth.py: no rate limiting — critical",
  "finding_b": "middleware.py: global rate limiting exists",
  "resolution": "human_review",
  "conflict_reason": "Unclear whether the middleware covers the auth endpoint"
}
```

## The Exam's Trap: "The Same Model Can Review Its Own Output"

The exam offers an option like:

> *"To cut cost we run both the extraction and the validation step in the same model session."*

**The problem with this approach:**
- Same session = same context = same blind spots
- The model finds its own earlier reasoning natural
- The benefit of independent review disappears

**The right approach:**
- A **separate API call** for the review (independent context)
- A second instance with a **different system prompt** for high-risk findings
- **Human validation** for critical decisions

## Full Architecture: A CI/CD Code Review Pipeline

```
PR opened
│
├─ [Parallel] Per-file analysis (N instances, one file each)
│   ├─ src/auth.py → {findings, confidence}
│   ├─ src/api.py  → {findings, confidence}
│   └─ src/db.py   → {findings, confidence}
│
├─ [Cross-file] Integration analysis (independent instance)
│   ├─ Data-flow check
│   ├─ Contradiction detection
│   └─ System-wide patterns
│
├─ [Routing] Confidence-based sorting
│   ├─ High confidence → automatic flagging
│   └─ Low confidence → human review queue
│
└─ [Output] PR comment + prioritised findings list
```

## Key Takeaways

| # | Key takeaway |
|---|---|
| 1 | **Self-review is limited** — same session, same blind spots. |
| 2 | **An independent instance** catches more subtle problems without carrying earlier context. |
| 3 | **Per-file analysis** prevents attention dilution — every file gets full attention. |
| 4 | **The cross-file integration pass** catches data-flow and contradiction problems. |

## Practice Questions with Explanations

### Question 1

A code review system validates each extraction in the same Claude session. What fundamental problem does it have?

**A)** The validation step is too expensive
**B)** Carrying its own reasoning context, the model may miss the same mistakes
**C)** Two calls can't be made in the same session
**D)** The output format changes

**✅ Answer: B**

*Explanation:* the model in the same session carries the context it used to produce the first extraction. That context increases the tendency to find its own mistakes "reasonable". An independent instance doesn't carry that context and catches subtle inconsistencies better.

---

### Question 2

What is the best architecture for analysing a large codebase (50 files)?

**A)** Give all 50 files to a single instance at once
**B)** Analyse each file in a separate instance, then run an independent cross-file integration pass
**C)** Analyse the 10 largest files, skip the rest
**D)** Split the files into groups of 5, send a separate batch per group

**✅ Answer: B**

*Explanation:* 50 files at once → attention dilution, inconsistent depth. Per-file analysis gives every file equal attention. The cross-file pass catches data-flow and inter-file contradictions. This two-stage architecture solves both problems.

---

### Question 3

How should confidence thresholds be calibrated in confidence-based routing?

**A)** Set based on developer intuition
**B)** Adjusted according to the model's suggestion
**C)** Confidence levels compared with real outcomes over a labelled validation set
**D)** Use industry-standard thresholds (80% confidence = high)

**✅ Answer: C**

*Explanation:* the decision "medium confidence → human review" must rest on data, not intuition. Over findings labelled by security experts, the correlation between the model's confidence levels and real error rates is measured. That yields a concrete threshold.

---

### Question 4

File A has a "no rate limiting — critical" finding. The cross-file pass finds a global rate-limiting middleware in file B. How should this be handled?

**A)** Auto-close the file A finding — the middleware exists
**B)** Can the middleware be bypassed? There's uncertainty → flag with conflict_detected: true, let a human review
**C)** Report both findings, ignore the contradiction
**D)** Re-analyse file A, start a retry loop

**✅ Answer: B**

*Explanation:* whether the middleware covers the auth endpoint can't be determined automatically. In such uncertainties, flagging with `conflict_detected: true` and routing to human review is the right approach. Auto-closing (A) creates a security risk; ignoring (C) doesn't resolve the contradiction.
