## The Core Idea

An agent exploring a large codebase runs for a long time. It reads files, inspects classes, maps dependencies. During that process **context degradation** is an inevitable problem. The agent starts losing the specific information it discovered early in the session and starts using generic phrases like "typical patterns".

This task statement teaches how to detect context degradation and how to prevent it with four different strategies.

---

## Context Degradation

### Symptoms

In long sessions you observe these changes in the agent's behaviour:

1. **Generalisation:** early in the session the agent reports specific findings like "the UserService.authenticate() method does no null check on line 3"; in later turns it starts using vague phrases like "authentication checks are generally done in this kind of service".

2. **Contradictory references:** the agent misremembers a class it discovered earlier or references a method that doesn't exist.

3. **Context saturation:** verbose exploration output (file lists, grep results, full file contents) fills the context and overwrites earlier findings.

### Why Does It Happen?

When the context window fills up, the oldest information starts dropping. Verbose tool results (full file contents, long grep output) consume the context quickly. Critical findings the agent discovered in turn 1 may no longer be in the context by turn 10.

---

## Four Mitigation Strategies

### 1. Scratchpad Files

Write the key findings to a file and reference that file for later questions.

```bash
# The agent writes its findings to a file during the session
echo "## Exploration Findings
- UserService.authenticate(): null check missing (line 47)
- PaymentGateway: no retry mechanism
- DatabasePool: max connection = 10, scaling problem
" > /tmp/findings.md
```

**Advantage:** findings persist independently of the context window. Even when the agent's context fills up, it can recover earlier findings by reading the file.

**When to use:** in a single agent's long exploration sessions. Simple and effective.

### 2. Subagent Delegation

Create subagents for specific investigations. The main agent maintains high-level coordination.

```
Coordinator Agent:
├── Subagent 1: "Analyse the authentication module"
├── Subagent 2: "Analyse the database layer"
└── Subagent 3: "Analyse the API endpoints"
```

**Advantage:** each subagent starts with a clean context — low risk of context degradation. The main agent only coordinates and merges results.

**When to use:** when parallel exploration is needed in large codebases. Directly linked to the multi-agent orchestration in Domain 1.

### 3. Summary Injection

Summarise the findings of one exploration phase and inject them into the subagents of the next phase.

```
Phase 1: Exploration → findings are summarised
    ↓
Summary injection → included in the subagent prompts
    ↓
Phase 2: Deep analysis (clean context + summary of earlier findings)
```

**Advantage:** enables information transfer between phases. Subagents know the earlier phase's findings but don't carry the verbose exploration output.

**When to use:** in multi-phase investigations — exploration → analysis → synthesis flows.

### 4. The /compact Command

When the context fills with verbose exploration output, reduce context usage with the `/compact` command.

**When to use:** when a context-saturation warning appears or the agent's responses show symptoms of context degradation.

**Exam note:** `/compact` alone isn't enough — it should be used together with scratchpad, subagents and summary injection.

## Crash Recovery

### Problem

While a multi-agent system runs, an agent crashes. The findings that agent collected so far are lost. When the system restarts, does everything get re-explored from scratch?

### Fix: A Manifest File

Each agent exports its structured state to a known file location (a manifest):

```json
// /tmp/agent_state/research_agent_manifest.json
{
  "agent_id": "research_agent_01",
  "phase": "analysis",
  "completed_tasks": [
    "source_collection",
    "initial_categorization"
  ],
  "pending_tasks": [
    "deep_analysis_geothermal",
    "cross_reference_check"
  ],
  "key_findings": [
    {"claim": "Solar grew 45%", "source": "IEA", "confidence": 0.95},
    {"claim": "Wind hit $120B", "source": "IRENA", "confidence": 0.88}
  ],
  "last_checkpoint": "2024-03-15T14:30:00Z"
}
```

### Recovery Flow

1. The coordinator restarts
2. Loads the manifest files
3. Injects each agent's state into the agent prompts
4. The agents continue from where they left off — not from scratch

**Rule:** each agent regularly writes its structured state to a manifest file. On a crash, the coordinator recovers by loading these manifests.

## Practice Scenario 1

> A developer has been running an agent session exploring a large codebase for 2 hours. At the start the agent reported specific findings like "there's a race condition in the PaymentService.process() method, the lock mechanism is missing on line 142".
>
> Now it uses vague phrases like "thread-safety concerns should generally be considered in this kind of service".
>
> **What is the most effective fix?**
>
> **A)** Use a model with a bigger context window.
>
> **B)** Add "always be specific" to the agent's system prompt.
>
> **C)** Write the key findings to a scratchpad file. Create subagents for the next research phases and inject the findings summary into the subagent prompts.
>
> **D)** End the session and start from scratch.

### Correct Answer: C

**Why C is correct:** classic context-degradation symptoms — the shift from specific findings to generic phrases. Three strategies applied together: persist the findings with a scratchpad, research in clean contexts with subagents, transfer information between phases with summary injection.

**Why A is wrong:** a bigger model delays the problem but doesn't fix it. After 4 hours the same degradation happens. A structural fix is needed.

**Why B is wrong:** a prompt instruction is probabilistic. The problem isn't the model being "lazy" but the specific information having physically dropped out of the context. If the information isn't in the context, "be specific" doesn't work.

**Why D is wrong:** starting from scratch loses the previous 2 hours of exploration entirely. Restarting without a findings-recovery mechanism is inefficient.

## Practice Scenario 2

> A multi-agent research system runs with 3 subagents. The system crashes. When restarted, the coordinator starts the subagents from scratch — the already completed 2-hour data-collection phase is repeated.
>
> **Which mechanism should have been in place to prevent this?**
>
> **A)** Use more reliable hardware — no crashes.
>
> **B)** Each agent regularly writes its structured state to a manifest file. During recovery the coordinator loads the manifest files and restarts the agents from where they left off.
>
> **C)** Store every agent's full conversation history in a database and restore it as-is during recovery.
>
> **D)** Reduce the number of agents — so a single agent's crash doesn't affect the whole system.

### Correct Answer: B

**Why B is correct:** the crash-recovery mechanism. Each agent writes structured state (completed tasks, pending tasks, key findings) to a manifest file. During recovery the coordinator loads these manifests and injects them into the agent prompts. The agents continue from where they left off, not from scratch.

**Why A is wrong:** hardware reliability reduces crashes but doesn't eliminate them. A recovery mechanism should exist in every system.

**Why C is wrong:** the full conversation history is very verbose — restoring the whole history during recovery immediately exhausts the context budget. A manifest file is structured and compact — it contains only the necessary state information.

**Why D is wrong:** reducing the number of agents doesn't solve crash recovery. Even a single agent can crash — a recovery mechanism is needed.
