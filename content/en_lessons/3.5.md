## The Core Idea

You gave Claude Code a task and the result isn't what you expected. How do you improve it? This task statement teaches techniques for **systematically** improving Claude Code's output.

---

## The Technique Hierarchy

There are three core techniques — ordered from most to least effective:

### 1. Concrete Input/Output Examples (Most Effective)

Show 2–3 examples — "given this input, produce this output." Beats prose explanations every time.

**Why most effective?** Claude Code is far better at generalising from examples than at inferring from prose explanations.

**Rule:** if prose explanations are interpreted inconsistently, switch to concrete input/output examples.

#### Bad Approach (Prose)
```
"Make the function names more descriptive and use camelCase."
```

#### Good Approach (Concrete Examples)
```
Example 1:
  Input:  function proc(d) { ... }
  Output: function processUserData(userData) { ... }

Example 2:
  Input:  function calc(a, b) { ... }
  Output: function calculateTotalPrice(basePrice, taxRate) { ... }

Example 3:
  Input:  function chk(u) { ... }
  Output: function checkUserPermissions(userId) { ... }
```

The model extracts the pattern from these examples and applies it consistently.

### 2. Test-Driven Iteration

Write the tests first, share the failing tests with Claude Code, steer the improvement.

**How it works:**
1. Write tests that define the expected behaviour
2. Run the code Claude Code produced against the tests
3. Show the failing tests to Claude Code
4. Claude Code improves the code until the tests pass

**Advantage:** the success criterion is clear and objective. No "is it good or bad" debate — the tests either pass or they don't.

### 3. The Interview Pattern

Ask Claude Code to **ask you questions** before implementing.

**When to use:** when working in an unfamiliar area. Claude Code's questions surface points you'd miss thinking alone.

**How it works:**
```
"Before designing this database schema, ask me questions about the
requirements. Design based on my answers."
```

Claude Code asks things like:
- "Is a many-to-many relationship needed?"
- "Will soft delete be used?"
- "Which fields should be indexed?"

These questions reveal missing requirements before you start the design.

## Feedback Timing Strategy

### Batch Feedback — In One Message

**When:** the fixes **interact** — changing one affects the others.

Example: "Rename the function, update the parameters and fix the call sites" — these are interdependent, give them in one message.

### Sequential Feedback — In Separate Messages

**When:** the problems are **independent** — fixing one doesn't affect the other.

Example: "Fix the indentation in file 1" and "Update the error message in file 2" — independent problems, give them in separate messages.

---

## Example-Based Communication — When Prose Fails

This scenario is tested directly:

> A developer describes a code transformation in prose. Claude Code interprets it differently every time.

**Fix:** drop the prose, switch to concrete input/output examples.

**Why?** Prose is ambiguous — what does "more descriptive" mean? What does "cleaner" mean? Everyone interprets it differently. Examples are precise — "given this input, produce this output." No room for interpretation.

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| Concrete input/output examples | The most effective technique — show 2–3 before/after examples |
| Test-driven iteration | Write tests, share failing tests, steer the improvement |

| Batch feedback | Interacting fixes → one message |
| Sequential feedback | Independent fixes → separate messages |

## Practice Scenario 1

> A developer gives Claude Code this instruction:
>
> *"Make the functions more readable and convert them to modern JavaScript syntax."*
>
> Claude Code produces a different result every time — sometimes it uses arrow functions, sometimes not; sometimes it destructures, sometimes not. Inconsistent.
>
> **Which technique should be tried first?**
>
> **A)** Add a more detailed prose explanation to the system prompt — explain at length what "modern" means.
>
> **B)** Give 2–3 concrete input/output examples — before/after examples of the form "given this old code, convert it to this modern code".
>
> **C)** Run Claude Code with a different model — a smarter model will be consistent.
>
> **D)** Create a separate command for each transformation — an arrow-function command, a destructuring command.

### Correct Answer: B

**Why B is correct:** the prose explanation is interpreted inconsistently — that is precisely the signal to switch to concrete examples. 2–3 before/after examples let the model extract the pattern and apply it consistently. "Modern" is ambiguous — examples are precise.

**Why A is wrong:** more prose, more ambiguity. The prose is already interpreted inconsistently — longer prose doesn't fix that, it adds complexity.

**Why C is wrong:** the problem is not the model's intelligence but the instruction's ambiguity. A different model also interprets an ambiguous instruction differently.

**Why D is wrong:** over-engineering. Creating a separate command for each transformation type adds complexity. 2–3 examples are far simpler and more effective.

## Practice Scenario 2

> A developer wants to improve an API endpoint Claude Code generated. There are two problems:
>
> 1. Error handling is missing — this affects the response format and control flow
> 2. The API documentation in the README is out of date — the endpoint's description is wrong
>
> **How should the feedback be given?**
>
> **A)** Give both problems in one message — batch feedback.
>
> **B)** Fix the error handling first (one message), then update the documentation (a separate message) — sequential feedback.
>
> **C)** Explain both in prose and let Claude Code decide the priority itself.
>
> **D)** Write tests for the error handling, give examples for the documentation — use different techniques.

### Correct Answer: B

**Why B is correct:** the two problems are independent — error handling concerns the code, documentation concerns the README. Fixing one doesn't affect the other. Independent problems → sequential feedback. Fix the error handling first (it affects the response format and flow, so it comes first), then fix the documentation based on the updated code.

**Why A is wrong:** batch feedback is for interacting fixes — when changing one affects the other. Here the problems are independent.

**Why C is wrong:** leaving prioritisation to Claude Code can produce inconsistent results. As the developer you should steer the flow.

**Why D is wrong:** using different techniques isn't wrong, but the question asks about feedback timing. The core point: independent problems → sequential. That is correct timing regardless of technique choice.
