## The Core Idea

Claude Code isn't only used interactively in the terminal — it can also be integrated into **CI/CD pipelines**. Tasks such as PR review, test generation and code analysis can run automatically. This task statement teaches **how to configure** CI/CD integration and its **common traps**.

---

## The `-p` Flag — Non-Interactive Mode (Print Mode)

This is the single most tested concept on the exam. **Memorise it.**

### Problem

This command runs in a CI/CD pipeline:

```bash
claude "Analyze this PR"
```

The pipeline **hangs forever.** The logs show Claude is **waiting for interactive input.**

### Fix

```bash
claude -p "Analyze this PR"
```

The `-p` flag runs Claude Code in **non-interactive mode** (print mode). It doesn't wait for interactive input; it prints the output directly and exits.

> **Run Claude Code in a CI pipeline without the `-p` flag and the pipeline hangs.** That simple.

---

## Structured CI Output

In CI/CD pipelines human-readable text isn't enough — automated systems want **machine-parseable** output.

### JSON Output

```bash
claude -p --output-format json "Review this code"
```

### Structured Findings via JSON Schema

```bash
claude -p --output-format json --json-schema '{"type":"object","properties":{"issues":{"type":"array"},"summary":{"type":"string"}}}' "Review this PR"
```

**Advantage:** automated systems can parse the findings and post them **as inline comments on the PR**.

## Session Context Isolation — The Same Session Can't Review Itself

This is very important and tested:

> **The same Claude session that generated the code is LESS EFFECTIVE at reviewing its own changes.**

### Why?

The same session carries the reasoning context it built while writing the code. That context makes it **less likely** to question its own decisions. It has already approved its own logic — reviewing again, it reaches the same conclusion.

### Fix

Use an **independent review instance** for code review. That session sees the code for the first time — it can review without bias.

```bash
# The session that generated the code
claude -p "Implement the user auth module"

# Review in a SEPARATE session — independent, unbiased
claude -p "Review the changes in this PR for security issues"
```

---

## Incremental Review Context

If you re-run the review when new commits arrive, **include the earlier review findings in the context** and instruct Claude to **report only new or still-unresolved issues.**

### Why?

If you don't include the earlier findings, Claude reports the same issues again → **duplicate comments** → erodes developer trust.

### The Right Approach

```bash
claude -p "Review this PR. Previous review findings: [earlier findings].
Report ONLY new or still-unaddressed issues."
```

## CLAUDE.md for CI

If Claude Code is invoked to generate tests in the CI/CD pipeline, it is critical that **the test standards are documented in CLAUDE.md**.

### What CLAUDE.md Should Contain

- Test standards — which framework, which patterns
- Valuable-test criteria — rules defining what should be tested
- Existing fixtures — what's available in the test infrastructure

### What Happens Without CLAUDE.md?

Claude Code produces **low-value boilerplate tests** — tests that don't exercise real business logic, just empty scaffolds.

## Practice Scenario 1

> A CI pipeline script runs this command:
>
> ```bash
> claude "Analyze this PR for potential bugs"
> ```
>
> The pipeline hangs forever. The logs show Claude is waiting for input.
>
> **What is the correct fix?**
>
> **A)** Wrap the command in a timeout wrapper — terminate automatically after 60 seconds.
>
> **B)** Add the `-p` flag — `claude -p "Analyze this PR for potential bugs"` — to run in non-interactive mode.
>
> **C)** Add an `echo "yes" |` pipe to the pipeline — answer "yes" automatically.
>
> **D)** Update the Claude Code version — it may be a bug in an old version.

### Correct Answer: B

**Why B is correct:** the `-p` flag runs Claude Code in non-interactive mode (print mode). It doesn't wait for interactive input; it analyses directly, prints the output and exits. Always use `-p` in CI/CD pipelines.

**Why A is wrong:** a timeout doesn't solve it — it cuts Claude's analysis short. The problem is Claude waiting for input; the fix is to stop it waiting (`-p`).

**Why C is wrong:** the `echo "yes"` pipe is unreliable and dangerous. Saying "yes" without even knowing what Claude asked bypasses the confirmation mechanism. The right fix is to turn interactive mode off entirely.

**Why D is wrong:** this isn't a bug, it's expected behaviour. Claude Code runs in interactive mode by default. In CI the `-p` flag is required.

## Practice Scenario 2

> A team does automated code review with Claude Code in its CI pipeline. The same pipeline:
> 1. First generates the code with Claude Code
> 2. Then reviews the generated code in the same session
>
> The review results are very positive — it finds almost no issues. But human reviewers find many problems in the same code.
>
> **What is the root cause?**
>
> **A)** Claude Code's review capabilities are inadequate — a different model should be used.
>
> **B)** The same session is reviewing the code it generated — carrying its reasoning context, it doesn't question its own decisions. An independent review session should be used.
>
> **C)** The review prompt is inadequate — more detailed review instructions should be added.
>
> **D)** Review standards are missing from CLAUDE.md.

### Correct Answer: B

**Why B is correct:** the session context isolation rule. The same session that generated the code carries its reasoning context — it already justified its own decisions; reviewing again it reaches the same conclusion. An independent review session sees the code for the first time and reviews without bias.

**Why A is wrong:** the problem isn't the model's ability but contextual bias. The same model reviews far more effectively in an independent session.

**Why C is wrong:** prompt improvement may help a little but doesn't fix the root cause. The same session is reviewing its own code — however good the prompt, the reasoning context creates bias.

**Why D is wrong:** CLAUDE.md matters, but the problem here is structural — session isolation. Even with standards, the same session falls short at questioning its own code.

## Practice Scenario 3

> A CI pipeline reviews every PR with Claude Code. When new commits arrive the review is re-run. Developers complain: "Claude reports the same issues every time — it repeats things I've already fixed."
>
> **What is the fix?**
>
> **A)** Use a different prompt on each run — Claude produces the same findings when it sees the same prompt.
>
> **B)** Run the review only against the latest commit — ignore earlier files.
>
> **C)** Include the earlier review findings in the context and instruct Claude to "report only new or still-unresolved issues".
>
> **D)** Reduce the review frequency — not every PR, once before merge.

### Correct Answer: C

**Why C is correct:** incremental review context. If you include the earlier findings, Claude knows what has already been reported and what has been fixed. With the "report only new or unresolved issues" instruction the duplicate comments disappear. Developer trust is preserved.

**Why A is wrong:** using a different prompt doesn't fix it — if Claude doesn't know the earlier findings, it rediscovers and reports the same issues.

**Why B is wrong:** looking only at the latest commit misses file-wide issues. A commit may have partially fixed a larger problem — the full context is needed.

**Why D is wrong:** reducing frequency doesn't solve the problem, it postpones it. And it loses the advantage of early feedback.
