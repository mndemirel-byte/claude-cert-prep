## The Core Idea

There are two ways to extract structured data:

1. **Prompt-based JSON:** instructing "respond in JSON format"
2. **JSON schema via tool_use:** defining a formal tool for Claude and forcing it to use it

The difference between the two is a matter of **reliability**. The exam expects you to understand the limits of that difference correctly — what it does and doesn't fix.

---

## The Reliability Hierarchy

### Syntactic Reliability

```
Tool_use + JSON schema  →  ELIMINATES syntax errors completely
Prompt-based JSON       →  The model can produce invalid JSON
```

**With tool_use Claude cannot produce invalid JSON** — the schema doesn't allow it. That means your downstream system won't crash with a parse error.

### Errors Tool_use Cannot Prevent

This is where the exam sets its trap. Tool_use doesn't fix everything.

```
❌ Semantic errors: line items say 500 + 300 = 900, but the line total is 750.
   → JSON valid, schema validated, but the numbers are wrong.

❌ Field-placement errors: the "unit price" value ended up in the "total price" field.
   → JSON valid, all fields filled, but values in the wrong place.

❌ Fabrication: the source document has no price, but the model invents a plausible value.
   → Especially high risk for "required" fields.
```

**Summary:** tool_use guarantees **syntax**. It does not guarantee **meaning**.

## Tool_choice Modes — Critical Distinctions

```json
"tool_choice": "auto"
// Default. The model may call a tool or return plain text.
// Use when the document type is unknown and a text response is acceptable.

"tool_choice": "any"
// The model MUST call a tool. It decides which one.
// You want guaranteed structured output but the document type varies → use this.

"tool_choice": {"type": "tool", "name": "extract_invoice"}
// The model MUST call this specific tool.
// Use for a mandatory first step or when a specific schema is required.
```

### The Exam's Favourite Question

> *"Documents arrive in unknown formats. Guaranteed structured output is needed. Which tool_choice?"*

**Answer: `"any"`** — the model chooses which tool to use but MUST call a tool.

## Schema Design — Preventing Fabrication

This is the exam's most detailed expectation. A good schema contains three things:

### 1. Optional/Nullable Fields

```json
{
  "name": "extract_invoice",
  "input_schema": {
    "type": "object",
    "properties": {
      "invoice_number": {
        "type": "string",
        "description": "Invoice number"
      },
      "payment_due_date": {
        "type": ["string", "null"],
        "description": "Payment due date. Return null if not in the document."
      },
      "discount_rate": {
        "type": ["number", "null"],
        "description": "Discount rate. Return null if not specified."
      }
    },
    "required": ["invoice_number"]
  }
}
```

**Why it matters:** if `payment_due_date` were required, the model would invent it when absent from the document. Making it nullable offers the "return null" option.

### 2. An "unclear" Enum Value for Ambiguous Cases

```json
{
  "severity": {
    "type": "string",
    "enum": ["critical", "major", "minor", "unclear"],
    "description": "Use 'unclear' if it cannot be determined from the available information."
  }
}
```

Without this the model always picks a value — even in ambiguous cases. The `"unclear"` option gives the model permission to say "I don't know".

### 3. "other" + Free Text — Extensible Classification

```json
{
  "document_type": {
    "type": "string",
    "enum": ["invoice", "receipt", "contract", "other"]
  },
  "document_type_detail": {
    "type": ["string", "null"],
    "description": "Explain if document_type is 'other'. Otherwise null."
  }
}
```

**Why it matters:** if you keep the enum closed, unknown documents are misclassified. "other" + a freeform field covers both worlds: structured classification + flexibility.

### 4. Format Normalisation Rules

In addition to the schema, specify format rules in the prompt:

```
"Return all dates in YYYY-MM-DD format.
Currency amounts as integers without decimals: '1,250.50' → 125050 (cents)
Phone numbers in +90XXXXXXXXXX format."
```

These rules can't be written into the schema — but they're mandatory for consistency.

## Full Schema Example: Invoice Extraction

```json
{
  "name": "extract_invoice_data",
  "description": "Extract structured data from an invoice document",
  "input_schema": {
    "type": "object",
    "properties": {
      "invoice_number": {
        "type": "string",
        "description": "Invoice number or reference code"
      },
      "invoice_date": {
        "type": ["string", "null"],
        "description": "Invoice date in YYYY-MM-DD format. Null if absent."
      },
      "vendor_name": {
        "type": "string",
        "description": "Seller/supplier name"
      },
      "total_amount": {
        "type": ["number", "null"],
        "description": "Total amount in cents. Null if it cannot be extracted."
      },
      "line_items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "description": {"type": "string"},
            "unit_price": {"type": ["number", "null"]},
            "quantity": {"type": ["number", "null"]},
            "total": {"type": ["number", "null"]}
          },
          "required": ["description"]
        }
      },
      "currency": {
        "type": "string",
        "enum": ["TRY", "USD", "EUR", "other"],
        "description": "Currency. 'other' if unknown."
      },
      "extraction_confidence": {
        "type": "string",
        "enum": ["high", "medium", "low"],
        "description": "The model's assessment of extraction quality"
      }
    },
    "required": ["invoice_number", "vendor_name"]
  }
}
```

## Exam Traps

### Trap 1: "Tool_use fixes everything"

*"We added tool_use to fix the validation problems."*

No. Tool_use fixes **syntax** problems. Semantic problems (wrong total, wrong field) need a validation-retry loop.

### Trap 2: "Required fields prevent hallucination"

*"We shouldn't make any field null, so there's no missing data."*

The opposite. If you make all fields required, the model is forced to invent values for missing information. Optional/nullable fields prevent fabrication.

### Trap 3: "`auto` gives guaranteed output"

No. With `auto` the model can also return a text response. For guaranteed structured output use `any` or force a specific tool.

---

## Key Takeaways

| # | Key takeaway |
|---|---|
| 1 | **Tool_use eliminates syntax errors** — the JSON is always valid. |
| 2 | **Tool_use does not prevent semantic errors, wrong fields, fabrication.** |
| 3 | **`auto`:** model picks text or tool. **`any`:** must call a tool. **Specific:** must call that tool. |
| 4 | **Optional/nullable fields prevent fabrication** — not required. |
| 5 | **The `"unclear"` enum value** gives the model permission to say "I don't know". |
| 6 | **`"other"` + freeform field** extends the schema for unknown categories. |
| 7 | **Format normalisation rules** go in the prompt, not the schema. |

## Practice Questions with Explanations

### Question 1

Which problem does using a JSON schema via tool_use definitely solve?

**A)** The model doesn't invent values
**B)** The JSON is always syntactically valid
**C)** Fields always carry the correct value
**D)** Extraction quality is guaranteed

**✅ Answer: B**

*Explanation:* tool_use only provides a syntax guarantee. The model can't produce broken JSON. But fabrication (A), wrong field values (C) and overall quality (D) can still be problems.

---

### Question 2

Documents arrive in different structures (invoice, contract, receipt). Different tools were defined per document type. Which tool_choice is correct?

**A)** `"auto"` — the model picks the most suitable tool, no structured-output guarantee
**B)** `"any"` — the model must call a tool, and decides which one
**C)** `{"type": "tool", "name": "extract_invoice"}` — force the invoice tool for every document
**D)** Make a separate API call per document type

**✅ Answer: B**

*Explanation:* `"any"` provides guaranteed structured output and the model picks the most suitable tool for the document type. `"auto"` (A) can return a text response. A specific tool (C) treats every document as an invoice.

---

### Question 3

In the invoice extraction schema the `payment_due_date` field was made `required`. What happens when invoices without a date are processed?

**A)** The model returns "null", which is safe
**B)** The model fails with a schema error
**C)** The model may invent a plausible date
**D)** The model returns an empty string

**✅ Answer: C**

*Explanation:* when the field is required and the source document has no information, the model thinks "I must put something in the required field" and invents a value. That's wrong data generation — it affects downstream systems. Fix: make it nullable with `"type": ["string", "null"]`.

---

### Question 4

A schema defines `"enum": ["invoice", "receipt", "contract"]` for document type. What happens when a new document type (lease agreement) is encountered?

**A)** The model returns an error and stops processing
**B)** The model assigns it to the closest existing category ("contract") — potential misclassification
**C)** The model returns a value outside the schema
**D)** The model refuses to process the document

**✅ Answer: B**

*Explanation:* because the model must conform to the schema, it forces the unknown type into an existing category. Fix: add an `"other"` enum value + a nullable `document_type_detail` field.
