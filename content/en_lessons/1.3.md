## The Core Idea

Task Statement 1.2 covered how the coordinator manages subagents. Now the real question: **how does the coordinator create subagents, and how does it pass them information?**

---

## The Task Tool

The coordinator's mechanism for creating subagents is the **Task tool**. Critical detail: if `"Task"` isn't in the coordinator's `allowedTools` list, it cannot spawn subagents — full stop.

Every subagent is defined by an **AgentDefinition**, which contains three things:

- **Description** — a short summary of what the subagent does
- **System prompt** — the subagent's behavioral rules and instructions
- **Tool restrictions** — which tools the subagent can access (only what it needs)

---

## Context Passing — The Most Critical Topic

Recall the isolation principle from 1.2: subagents inherit nothing automatically. So how does the coordinator pass information? Three core rules:

### Rule 1: Include Prior Agent Findings Directly in the Prompt

For example, if you're having a synthesis agent write a report, you need to copy the web search agent's results and the document analysis agent's extracted findings directly into the synthesis agent's prompt. The synthesis agent doesn't "know" about them — it can't see anything you don't give it.

### Rule 2: Use Structured Data Formats — Separate Content from Metadata

This is heavily tested. Sending subagents raw text isn't enough. Source URLs, document names, and page numbers need to travel separately from the content, in a structured format, so attribution survives the handoff between agents.

Bad example:
```
"The global solar market grew 25% in 2024 according to some reports."
```

Good example:
```json
{
  "claim": "The global solar market grew 25% in 2024",
  "source_url": "https://iea.org/reports/solar-2024",
  "document": "IEA Solar Market Report 2024",
  "page": 12
}
```

### Rule 3: State Goals and Quality Criteria, Not Step-by-Step Procedures

Coordinator prompts should specify research goals and quality bars, not procedural, step-by-step instructions. This lets the subagent adapt to what it actually finds.

- **Wrong:** "First search for X, then read Y, then write Z."
- **Right:** "Research developments in renewable energy from the last 2 years. Cite a source for every claim. Cover at least 5 different energy types."

---

## Parallel Spawning — Speed Optimization

The coordinator can make **multiple Task tool calls in a single turn**. This spawns subagents **in parallel**.

For example, in one turn the coordinator can:

- Task tool → spawn the web search agent
- Task tool → spawn the document analysis agent

This is much faster than spawning each one sequentially across separate turns. The exam tests latency awareness — parallel spawning is always the preferred approach when subagents don't depend on each other's output.

---

## fork_session

`fork_session` creates **independent branches** from a shared analysis baseline.

Use case: you want to compare two different testing strategies starting from the same codebase analysis. `fork_session` lets you branch off from that common starting point into two independent paths. Each branch runs independently of the other after the split.

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| Task tool | The subagent-creation mechanism — must be in the coordinator's `allowedTools` |
| AgentDefinition | Description + system prompt + tool restrictions |
| Context passing | Include prior agent findings directly in the prompt, with structured metadata |
| Structured metadata | Claim-source pairing — separate content from metadata (URL, document name, page) |
| Coordinator prompts | State goals and quality criteria, not step-by-step instructions |
| Parallel spawning | Multiple Task tool calls in one turn → subagents start in parallel → faster |
| fork_session | Creates independent branches from a shared analysis baseline |

## Practice Scenario

> A multi-agent research system exists. The web search subagent and document analysis subagent both work perfectly — each produces rich, well-sourced data. But the final report produced by the synthesis subagent has many claims **without attribution** — it's unclear where each piece of information came from.
>
> **What's the root cause, and how do you fix it?**
>
> **A)** The synthesis subagent's system prompt doesn't ask for attribution — add an instruction to "cite a source for every claim."
>
> **B)** The coordinator's context-passing mechanism doesn't include structured metadata — the subagents' output should be converted into a structured format that pairs each claim with its source.
>
> **C)** The web search subagent isn't returning source URLs — add URLs to the search results.
>
> **D)** The synthesis subagent should be given the coordinator's full conversation history so it can see the sources.

### Correct Answer: B

**Why B is correct:** The problem is in *how* the information is passed along. The web search and document analysis agents are working correctly — they're producing the data. But the coordinator is passing that data to the synthesis agent as plain text, without including the metadata (source URL, document name, page number) in a structured, parseable way. The synthesis agent sees raw text but can't tell which claim came from which source. The fix: convert the subagents' output into a structured format that pairs each claim with its source.

**Why A is wrong:** Adding a prompt instruction might help, but it isn't the root cause. Even if you tell the synthesis agent to "cite sources," if the data it receives doesn't carry structured source information, there's nothing to attribute. A prompt instruction can't invent missing data.

**Why C is wrong:** The scenario explicitly states the web search subagent works perfectly and produces rich, well-sourced data. The problem isn't at the source — it's in the coordinator's hand-off mechanism.

**Why D is wrong:** This is the isolation-principle trap. Giving a subagent the coordinator's full conversation history is not the correct architectural approach — it violates the isolation principle. The fix is for the coordinator to do context passing with structured metadata, not to break isolation.
