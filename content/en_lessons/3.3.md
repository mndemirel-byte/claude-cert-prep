## The Core Idea

Sometimes rules must apply to specific **file types** — all test files, all API files, all Terraform files. These files can be scattered across the codebase. Directory-level CLAUDE.md files fall short here because they are bound to a single directory. Path-specific rules solve exactly this problem.

---

## `.claude/rules/` Files and YAML Frontmatter

You put rule files in the `.claude/rules/` directory. At the top of each file you specify a **glob pattern** in YAML frontmatter:

```yaml
---
paths: ["terraform/**/*"]
---

In all Terraform files:
- Use a descriptive name for every resource
- Organise modules in separate directories
- Keep the state file in a remote backend
```

```yaml
---
paths: ["**/*.test.tsx"]
---

In all test files:
- Use the describe/it structure
- Each test should test a single behaviour
- Define mocks at the top of the file
- Test names should start with "should"
```

**Rules are loaded only while editing files that match the glob pattern.** If you're not touching a Terraform file, the Terraform rules aren't loaded.

---

## Directory-Level CLAUDE.md vs Path-Specific Rules

This distinction is an exam favourite. Learn it precisely:

| Property | Directory-level CLAUDE.md | Path-specific rules (`.claude/rules/`) |
|---|---|---|
| Scope | **A single directory** | **The whole codebase** (via glob pattern) |
| Matching | The directory the file is in | The file path pattern |
| Test files | You'd need a CLAUDE.md in every directory | `**/*.test.tsx` catches them all |
| Token efficiency | Always loaded while in that directory | Loaded only for matching files |

### The Critical Difference

**Glob patterns match files across the whole codebase.** The `**/*.test.tsx` pattern catches ALL test files, whatever directory they're in.

**A directory-level CLAUDE.md applies only to files in that one directory.** If test files are spread across 50 directories, you'd need 50 CLAUDE.md files — impossible to maintain.

---

## Token Efficiency

A major advantage of path-specific rules: **they are loaded only while editing matching files.**

- Not touching a Terraform file → Terraform rules not loaded
- Not editing a test file → test rules not loaded
- Compared with an always-loaded CLAUDE.md: **less unnecessary context, less token consumption**

---

## Use Cases

### Test Rules
```yaml
---
paths: ["**/*.test.tsx", "**/*.test.ts", "**/*.spec.ts"]
---
```
Rules applied to all test files — regardless of directory.

### API Rules
```yaml
---
paths: ["src/api/**/*", "src/routes/**/*"]
---
```
Rules specific to API and route files.

### Infrastructure Rules
```yaml
---
paths: ["terraform/**/*", "infrastructure/**/*"]
---
```
Rules specific to infrastructure configuration files.

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| `.claude/rules/` + YAML frontmatter | Define path-specific rules with glob patterns |
| Glob pattern | `**/*.test.tsx` — catches test files across the whole codebase |
| Directory CLAUDE.md limitation | Applies to a single directory only — inadequate for scattered files |
| Token efficiency | Loaded only while editing matching files — less unnecessary context |
| Exam trap | "Apply rules to test files in 50 directories" → path-specific rules, not directory CLAUDE.md |

## Practice Scenario 1

> In a codebase, test files are co-located with source files. There are test files in more than 50 directories. The team wants all tests to follow the same rules: describe/it structure, single-behaviour tests, mocks at the top of the file.
>
> **What is the right approach?**
>
> **A)** Create a path-specific rule file in `.claude/rules/` with the glob pattern `paths: ["**/*.test.tsx"]`.
>
> **B)** Put a separate `CLAUDE.md` in each of the 50 directories — with the test rules in each.
>
> **C)** Write all test rules in a single root `CLAUDE.md` — always loaded.
>
> **D)** Create a `/test-rules` skill — invoked whenever writing a test.

### Correct Answer: A

**Why A is correct:** the `**/*.test.tsx` glob pattern catches test files across the whole codebase — whatever directory they're in. One rule file applies to all test files in 50+ directories. Easy to maintain, token-efficient (loaded only while editing a test file).

**Why B is wrong:** 50 separate CLAUDE.md files in 50 directories is a maintenance nightmare. Changing one rule means updating 50 files. This is exactly the problem path-specific rules solve.

**Why C is wrong:** the root CLAUDE.md is always loaded — the test rules occupy context even when you're not editing a test file. Token waste and context pollution, plus irrelevant information in non-test files.

**Why D is wrong:** skills are invoked on demand — you'd have to remember to invoke it every time you write a test. Easy to forget. Path-specific rules load automatically — they kick in by themselves when a matching file is edited.

## Practice Scenario 2

> A team's Terraform configuration files are in `infrastructure/terraform/`. There are also Terraform modules in `modules/`. The team wants the same naming and organisation rules in all Terraform files.
>
> **Which approach fits best?**
>
> **A)** Create a directory-level `infrastructure/terraform/CLAUDE.md`.
>
> **B)** Create `.claude/rules/terraform.md` — with the frontmatter `paths: ["**/*.tf", "**/*.tfvars"]`.
>
> **C)** Add the Terraform rules to the root CLAUDE.md.
>
> **D)** Write the rules as a comment at the top of every Terraform file.

### Correct Answer: B

**Why B is correct:** the Terraform files are in two different directories (`infrastructure/terraform/` and `modules/`). The glob pattern `**/*.tf` catches files in both. One rule file applies to all Terraform files. Token-efficient — loaded only while editing a `.tf` file.

**Why A is wrong:** a directory-level CLAUDE.md applies only to files in `infrastructure/terraform/`. Terraform files in `modules/` don't get the rules. You'd need a second CLAUDE.md — path-specific rules solve this with one file.

**Why C is wrong:** the root CLAUDE.md is always loaded. Even while editing a Python file the Terraform rules sit in context — token waste.

**Why D is wrong:** in-file comments are not Claude Code's configuration mechanism. Hard to maintain, no standardisation.
