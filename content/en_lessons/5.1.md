## The Core Idea

Agents work across long conversations, accumulate tool results and make decisions based on information from earlier turns. During that process, **losing critical information** is the most common and most dangerous mistake. This task statement teaches how to prevent context loss.

On the exam these concepts appear especially in the **Customer Support Resolution Agent** and **Multi-Agent Research System** scenarios.

---

## The Progressive Summarisation Trap

In long conversations the history can be summarised to manage the token budget. That's exactly where the danger begins.

### Problem

During summarisation, numeric values, dates, percentages and customer expectations turn into **vague phrases**:

| Original information | Summarised form |
|---|---|
| "Customer wants a $247.83 refund for order #8891, placed on 3 March" | "customer wants a refund for a recent order" |
| "Customer expects a 15% discount, spent $1,200 across the last 3 orders" | "customer wants a discount, regular customer" |

Order number, amount, date — all gone. When the agent later has to work with this vague summary it can't perform the correct operation.

### Fix: A Persistent "Case Facts" Block

Extract the transactional facts into a separate structured block. Include this block **in every prompt** and **never summarise it**.

```json
{
  "case_facts": {
    "customer_name": "Ahmet Yılmaz",
    "order_id": "#8891",
    "order_date": "2024-03-03",
    "refund_amount": 247.83,
    "refund_currency": "USD",
    "customer_expectation": "full refund to original payment method",
    "loyalty_tier": "Gold",
    "total_spend_last_12m": 1200.00
  }
}
```

**Basic rule:** the conversation history may be summarised. Case facts are **NEVER** summarised.

## The "Lost in the Middle" Effect

### Problem

Models reliably process the **beginning** and **end** of long inputs. But findings **buried in the middle** can be missed.

Think: a 10-page research report with 7 different sources. A critical statistic is hidden in the middle of source 5. The model may skip it — an attention mechanism that looks at the beginning or the end misses it.

### Fix

Two methods applied together:

1. **Put a summary of the key findings at the TOP.** At the very top of the long input, provide a short summary of the most important findings.
2. **Use explicit section headers.** Split the content into structured sections — the model can use section headers as reference points.

```
## KEY FINDINGS SUMMARY
- Geothermal capacity grew 23% (Source: IEA 2024)
- Wind investments reached $120B (Source: IRENA)
- Solar panel cost fell 14% (Source: BloombergNEF)

## DETAILED FINDINGS
### 1. Geothermal Energy
[detailed content...]

### 2. Wind Energy
[detailed content...]
```

## Tool Result Trimming

### Problem

An order lookup tool returns more than 40 fields: internal IDs, logistics codes, warehouse info, tax details... But the agent only needs 5 fields.

As these verbose results are added to the context the **token budget is exhausted** and the truly important information gets lost under accumulated irrelevant data.

### Fix

Trim tool results to the relevant fields **BEFORE** adding them to the context:

```python
# WRONG: add the raw result to the context as-is
context.append(order_lookup_result)  # 40+ fields

# RIGHT: filter to the necessary fields only
relevant_fields = {
    "order_id": result["order_id"],
    "status": result["status"],
    "total": result["total"],
    "date": result["order_date"],
    "items": result["line_items"]
}
context.append(relevant_fields)  # 5 fields
```

This prevents token-budget exhaustion from accumulated irrelevant data.

## The Full History Requirement

### Rule

Consecutive API requests must include the **full conversation history**. Dropping earlier messages breaks conversational coherence.

### Why?

The Claude API is stateless — every request is independent. If you don't send the earlier messages, the model loses the conversation's context:

- If the user says "in addition to my earlier question..." in turn 3, without the turn 1 and 2 messages the model can't know what was asked
- If decisions depend on tool results from earlier turns, those results must be in the history

**Exception:** when the history grows too long, the **content of old turns can be summarised** — but the case facts block ALWAYS stays intact.

## Upstream Agent Optimisation

### Problem

A research agent returns a 3-page detailed analysis and chain of thought. This result is passed to a downstream agent with a limited context budget. The 3 pages of verbose content exhaust the downstream agent's context.

### Fix

Modify the upstream agents to return **structured data** instead of verbose content and chains of thought:

```json
{
  "key_facts": [
    {"claim": "Solar capacity grew 45%", "confidence": 0.95},
    {"claim": "Wind investments hit $120B", "confidence": 0.88}
  ],
  "citations": [
    {"source": "IEA Report 2024", "url": "https://...", "page": 12}
  ],
  "relevance_score": 0.92,
  "coverage_gaps": ["Geothermal data unavailable"]
}
```

| Approach | Result |
|---|---|
| Return verbose | The downstream agent exhausts its context budget |
| Return structured data | Key information preserved, budget used efficiently |

This is especially critical when downstream agents have limited context budgets.

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| Progressive summarisation trap | Summarisation turns numbers, dates, percentages into vague phrases |
| Case facts block | Keep transactional facts in a separate block, NEVER summarise |
| Lost in the middle | Findings buried in the middle can be missed → put key findings at the top |
| Section headers | Explicit section headers create reference points for the model |
| Tool result trimming | Trim verbose results to relevant fields, THEN add to context |
| Full history | Send the full conversation history in API requests — for coherence |
| Upstream optimisation | Modify agents to return structured data instead of verbose output |

## Practice Scenario 1

> A customer support agent is running a conversation of more than 15 turns. The history is summarised regularly to manage the token budget. In turn 12 the agent asks the customer "Which order are you requesting a refund for?" — even though the customer clearly stated the order number, amount and date in turn 2.
>
> **What are the root cause and the fix?**
>
> **A)** The model's context window is too small — use a bigger model.
>
> **B)** Transactional facts such as order number, amount and date were lost during summarisation. Fix: extract them into a persistent "case facts" block and never summarise it.
>
> **C)** Add "never forget customer details" to the agent's system prompt.
>
> **D)** Reduce the summarisation frequency — summarise every 15 turns, not every 5.

### Correct Answer: B

**Why B is correct:** the classic progressive summarisation trap. During summarisation the numeric values became vague phrases. Fix: extract the transactional facts (order no, amount, date) into a separate case facts block, include it in every prompt, never summarise it.

**Why A is wrong:** the problem isn't the context window size but the summarisation strategy. A bigger model with the same summarisation strategy loses the same information.

**Why C is wrong:** a prompt instruction is probabilistic. Saying "don't forget" is a prompt fix for a structural problem — if the summarised information has been physically removed from the context, the instruction does nothing.

**Why D is wrong:** reducing the summarisation frequency delays the problem but doesn't fix it. The same information loss happens at turn 15.

## Practice Scenario 2

> In a multi-agent research system the web search agent passes results to the synthesis agent. For every query the web search agent returns a 3-page detailed analysis, chain of thought and alternative interpretations. The synthesis agent's context budget is limited to 8K tokens.
>
> The synthesis agent reports an "insufficient context" error after 3 sources — it needs to analyse 5.
>
> **What is the most effective fix?**
>
> **A)** Raise the synthesis agent's context budget to 32K tokens.
>
> **B)** Modify the web search agent to return structured data (key facts, citations, relevance score) — instead of verbose content and chains of thought.
>
> **C)** Add "write a summary, don't give detail" to the synthesis agent.
>
> **D)** Reduce the number of sources to 3 — it fits the budget.

### Correct Answer: B

**Why B is correct:** upstream agent optimisation. The problem isn't in the synthesis agent but in the web search agent's verbose output. Modifying the agent to return structured data — key facts, citations, relevance score — uses the token budget efficiently and covers all 5 sources.

**Why A is wrong:** raising the budget is expensive and doesn't fix the underlying problem. Verbose content still wastes tokens — at 10 sources the same problem returns.

**Why C is wrong:** looking for the fix in the wrong place. The problem isn't the synthesis agent's output but its input. The incoming data is already verbose — instructing the synthesis agent doesn't change that.

**Why D is wrong:** narrowing the scope lowers quality. If 5 sources are needed, cutting to 3 means incomplete research.
