## The Core Idea

When Claude works as an agent, it has access to **tools** — functions such as querying a database, fetching customer data, sending an email or calling an API. You define these tools and hand them to Claude through the API.

The critical point: **Claude decides which tool to call almost entirely by reading the tool's description.** Not its name. Not the examples in the system prompt. The **description** is THE mechanism.

Think of it this way: you are in a dark room with 6 unlabelled buttons. Someone reads you a one-sentence description of each button. You must press the right one based on those descriptions alone. If two descriptions sound alike, you will sometimes press the wrong button.

That is exactly Claude's situation with poorly written tool descriptions.

---

## What Does a Good Tool Description Contain?

Five essential components:

1. **What the tool does** — its primary purpose, stated clearly
2. **What inputs it expects** — formats, types, constraints
3. **Example queries it handles well** — concrete use cases
4. **Edge cases and limitations** — what it does NOT do
5. **Explicit boundaries** — WHEN to use this tool versus similar ones

### Bad Description

```
get_customer: "Retrieves customer information."
```

### Good Description

```
get_customer: "Retrieves customer profile data (name, email, account tier,
preferences) by customer ID or email address. Use for identity-focused
queries such as 'who is this customer' or 'what plan are they on'. Do NOT
use for order-related queries — use lookup_order instead."
```

The difference: the second one tells Claude exactly when to pick this tool and when NOT to.

## The Misrouting Problem — An Exam Favourite

The exam loves this scenario: two tools with similar descriptions, and Claude keeps choosing the wrong one.

### Example Scenario

- `get_customer`: "Retrieves customer information"
- `lookup_order`: "Retrieves order information"

User: *"Check the status of order 12345."*

Claude picks `get_customer`. Why? Both descriptions say "retrieves … information" and the query is ambiguous. The descriptions are too vague for Claude to differentiate.

### Four Candidate Fixes and Their Verdict

| Fix | Verdict | Why |
|---|---|---|
| **Expand the tool descriptions** | **✅ Correct** | Low effort, high leverage. Directly fixes the root cause. |
| Add few-shot examples to the system prompt | ❌ Wrong | Adds token cost instead of fixing the description problem. Treats the symptom. |
| Add a routing classifier before Claude | ❌ Wrong | Over-engineering for a first step. You haven't tried the simple fix yet. |
| Merge the two tools | ❌ Wrong | Too much effort, breaks separation of concerns. |

> **Exam principle: the exam prefers low-effort, high-leverage fixes as the first step.** Better descriptions before a classifier. Always.

## Tool Splitting

Sometimes the opposite problem occurs — a tool is too broad. A single `analyze_document` tool summarises, extracts data AND verifies claims — three jobs at once.

### Fix: Split into Purpose-Specific Tools

- `extract_data_points` — pulls structured data from a document
- `summarize_content` — produces a summary
- `verify_claim_against_source` — checks whether a specific claim is supported by the source

Each tool does one job, is precisely described and has a defined input/output contract.

---

## System Prompt Conflicts — The Sneaky Trap

Even with perfect tool descriptions, **keyword-sensitive instructions in the system prompt can override them.**

Example: if the system prompt says "whenever the user mentions an order, always check the customer identity first", Claude may route order queries to `get_customer` regardless of the tool descriptions.

**Rule:** after updating tool descriptions, always review the system prompt for conflicts.

---

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| Tool description | THE mechanism for Claude's tool selection |
| Good description | What it does + inputs + examples + limitations + explicit boundaries |
| Misrouting | Similar descriptions → wrong tool selection. First fix: expand descriptions |
| Tool splitting | Split a broad tool into purpose-specific tools |
| System prompt conflict | Prompt instructions can override good descriptions — check for conflicts |
| Exam principle | Low effort, high leverage → descriptions before a classifier, splitting before merging |

## Practice Scenario

> An agent has two tools: `search_knowledge_base` and `search_tickets`. Both descriptions say "Searches relevant information". Users report that support-ticket queries frequently go to the knowledge base.
>
> A developer proposes adding a routing classifier that analyses the query and routes it to the right tool before Claude sees it.
>
> **Is this the right first step? Why?**
>
> **A)** Yes — the routing classifier analyses the query and routes it to the right tool, fixing misrouting.
>
> **B)** No — expand the tool descriptions first. Add explicit boundaries such as "use for FAQs, product documentation, how-to guides" to `search_knowledge_base` and "use for existing support tickets, complaint history, open cases" to `search_tickets`.
>
> **C)** No — merge the two tools into a single `search_all` tool.
>
> **D)** No — add 5 few-shot examples to the system prompt showing when to use each tool.

### Correct Answer: B

**Why B is correct:** The root cause is vague descriptions — both tools say "searches relevant information". Claude cannot differentiate. Expanding descriptions is a low-effort, high-leverage fix that targets the root cause directly.

**Why A is wrong:** A routing classifier is over-engineering for a first step. You haven't tried the simple fix (better descriptions). A classifier adds complexity and maintenance cost.

**Why C is wrong:** Merging breaks separation of concerns. Combining two different data sources (knowledge base and tickets) into one tool loses tool focus.

**Why D is wrong:** Few-shot examples add token cost and treat the symptom, not the root cause. While descriptions are vague, examples do not provide a reliable fix.
