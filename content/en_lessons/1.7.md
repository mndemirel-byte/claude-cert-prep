## The Core Idea

Agents can run for a long time. Sometimes you need to step away from a session and come back to it later. Or an agent has been running for a while and its context has started to degrade. This task statement answers the question: **how do you manage a session?**

---

## Three Options

### Option 1: Resume (--resume <session-name>)

Continues a specific session exactly where it left off. All prior context — tool calls, results, Claude's reasoning — is preserved as-is.

**When to use it:** The prior context is still valid and the files haven't meaningfully changed. For example, you paused a research session and are picking it back up the next day — the data is still current.

### Option 2: fork_session

Creates **independent branches** from a shared analysis baseline.

**When to use it:** You want to try different approaches from the same starting point. For example, comparing two different refactoring strategies starting from the same codebase analysis. Each branch runs independently of the others.

### Option 3: Fresh Start with Summary Injection

You start a new session, but inject a **structured summary** of prior findings into the starting context. It doesn't rediscover everything from scratch — it picks up the prior knowledge as a summary and continues from there.

**When to use it:** Tool results have gone stale, files have changed, or context quality has degraded over a long session.

---

## The Stale Context Problem (Exam Trap)

This one matters a lot. A developer resumes a session, but has changed files in the meantime. The agent reasons based on outdated tool results — it gives advice about code that no longer exists, or offers contradictory recommendations.

**The fix:** If you're resuming and files have changed, **tell the agent specifically which files changed** so it can do a targeted re-analysis. Don't ask it to rediscover everything from scratch.

**But if the changes are extensive, or the tool results are completely stale** → a fresh start with summary injection is more reliable.

---

## Decision Table

| Situation | Correct Approach |
|---|---|
| Context is still valid, files unchanged | **Resume** |
| Trying different approaches from the same baseline | **fork_session** |
| Tool results stale, files changed, context degraded | **Fresh start with summary injection** |
| Resume + a few files changed | Resume + **report the specific file changes** |

---

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| Resume | Context still valid, files unchanged → continue where you left off |
| fork_session | Independent branches from a shared baseline — for comparing different approaches |
| Fresh start with summary injection | Stale context, changed files → new session + a structured summary of prior findings |
| Stale context problem | Contradictory advice after resume → the agent is relying on stale tool results |
| Reporting specific file changes | Resume + files changed → tell the agent exactly which files changed |
| Exam trap | Solutions like "rediscover everything from scratch" or "use a bigger model" don't fix the problem |

## Practice Scenario

> A developer resumes an agent session working on a codebase. In the meantime, they made significant changes to 3 files. The agent gives contradictory advice about these files — at one point saying "refactor this function," even though the function has already been changed.
>
> **What's the problem, and what's the correct approach?**
>
> **A)** The agent's context window is too small — use a bigger model.
>
> **B)** The agent is reasoning based on stale tool results — when resuming the session, the changed files should be reported specifically, or if the tool results are entirely stale, do a fresh start with summary injection.
>
> **C)** Add an instruction to the agent's system prompt to "recheck the files."
>
> **D)** Create two branches with fork_session and pick the better result.

### Correct Answer: B

**Why B is correct:** The agent is reasoning based on outdated tool results — the files have changed, but the agent doesn't know. The fix has two layers: if the changes are limited, resume and report the specific file changes; if the changes are extensive or the context is thoroughly degraded, do a fresh start with summary injection.

**Why A is wrong:** The problem isn't context window size, it's stale data. A bigger model would make the same mistakes reasoning from the same outdated data.

**Why C is wrong:** A prompt instruction is probabilistic and tries to fix the problem in the wrong place. The real issue is that the data in the agent's context is stale.

**Why D is wrong:** fork_session is for comparing different approaches. The problem here is stale context — even if you branch, both branches would start from the same stale data.
