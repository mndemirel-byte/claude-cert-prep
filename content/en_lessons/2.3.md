## The Core Idea

How many tools do you give an agent? All of them, or only the ones it needs? This task statement answers exactly that question.

---

## The Tool Overload Problem

Give an agent 18 tools and selection reliability drops. Claude struggles to decide which tool to use when.

**Optimal:** **4–5 tools** per agent, scoped to its role.

Basic rule: **each agent should have only the tools its role requires.**

- The synthesis agent should not have web search tools
- The web search agent should not have document analysis tools
- Each agent has a tool set focused on its own job

---

## tool_choice Configuration

There are three modes — the exam expects you to distinguish them:

### 1. `"auto"` (Default)
The model decides **for itself** whether to call a tool. It can answer with plain text instead of calling a tool.

**When to use:** general operation. Sufficient in most cases.

### 2. `"any"`
The model **must** call a tool, but decides which one.

**When to use:** when you want **guaranteed structured output** from one of several schemas. The model must call a tool rather than return text.

### 3. `{"type": "tool", "name": "extract_metadata"}`
The model **must** call this specific tool. No choice.

**When to use:** to enforce mandatory first steps. For example, forcing metadata extraction before enrichment steps.

### Summary Table

| Mode | Behaviour | Use case |
|---|---|---|
| `"auto"` | Model decides — tool or text | General operation, default |
| `"any"` | Must call a tool, chooses which | Guaranteed structured output |
| `{"type":"tool","name":"X"}` | Must call the named tool | Mandatory first steps |

## Scoped Cross-Role Tools — AN EXAM QUESTION

This pattern is tested directly. Learn the scenario and the fix.

### Problem

A synthesis agent frequently returns control to the coordinator for simple fact verification. Each time this adds 2–3 extra round-trips and total latency rises by **40%**. **85%** of the verifications are simple lookups.

### Fix: A Scoped verify_fact Tool

Give the synthesis agent a **scoped `verify_fact` tool** — it can only do simple lookups. Complex verifications still route through the coordinator.

**Result:**
- Coordinator round-trip latency disappears for 85% of cases
- The remaining 15% of complex verifications still flow through the coordinator
- Latency drops significantly, architectural integrity is preserved

### Why the Other Fixes Are Wrong

| Fix | Why wrong |
|---|---|
| Give the synthesis agent all verification | Too broad — error risk on non-trivial verifications |
| Make the coordinator faster | Does not fix the structural latency — the round-trip is still there |
| Remove the verification step | Loss of functionality — verification is an important quality step |
| Give the synthesis agent full fetch_url | Too broad — security risk, loss of focus |

---

## Replacing Generic Tools with Constrained Alternatives

Instead of giving subagents generic tools, give constrained alternatives:

- ❌ `fetch_url` — can fetch any URL, security risk
- ✅ `load_document` — only validates and fetches document URLs

Safer, more focused, less error risk.

## Practice Scenario

> A synthesis agent frequently needs to verify claims while writing the final report. For each verification it hands control to the coordinator, the coordinator calls the web search subagent, and the result comes back. This adds 2–3 round-trips per task and raises total latency by 40%. 85% of the verifications are simple lookups of the form "is X true?".
>
> **What is the right way to reduce latency?**
>
> **A)** Run the coordinator on a faster model.
>
> **B)** Give the synthesis agent a scoped `verify_fact` tool — simple lookups are resolved directly in the agent, complex verifications flow through the coordinator.
>
> **C)** Remove the verification step — let the synthesis agent write the report without verification.
>
> **D)** Give the synthesis agent the full `fetch_url` tool — let it do all verification itself.

### Correct Answer: B

**Why B is correct:** 85% of cases are simple lookups — going to the coordinator for these creates needless latency. The scoped `verify_fact` tool resolves simple verifications in the agent; complex ones still flow through the coordinator. Latency drops, architectural integrity is preserved.

**Why A is wrong:** A faster model does not change the round-trip structure. Every verification still goes through the coordinator — slightly faster, but the structural latency remains.

**Why C is wrong:** Loss of functionality. Verification is an important step that protects report quality — removing it does not solve the problem, it creates a new one.

**Why D is wrong:** `fetch_url` is too broad — it can fetch any URL and creates a security risk. The constrained tool (`verify_fact`) is the safe, focused alternative.
