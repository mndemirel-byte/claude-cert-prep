## The Core Idea

Agentic loops, multi-agent orchestration, context passing — all of these rely on Claude making **flexible** and **intelligent** decisions. But some decisions can't be left to flexibility. Some rules must hold **every single time, no exceptions**.

That's exactly what this task statement teaches: **when do you trust Claude, and when do you enforce something programmatically?**

---

## The Enforcement Spectrum

There are two approaches:

### Prompt-Based Guidance (Probabilistic)

You write an instruction into the system prompt — "always verify the customer first." This works most of the time. But it isn't a 100% guarantee. Claude can occasionally skip it. Non-zero failure rate.

### Programmatic Enforcement (Deterministic)

You write a gate or hook in code — a prerequisite gate that checks whether the `verify_identity` tool has completed successfully before the refund tool can be called. If verification hasn't happened, the refund tool physically cannot run. 100% guarantee.

---

## The Exam's Decision Rule

This is very clear-cut and tested repeatedly:

- **If the consequences are financial, security-related, or compliance-related** → **Programmatic enforcement.** Always.
- **If the consequences are low-risk** (formatting preferences, style rules) → Prompt-based guidance is sufficient.

> The exam will offer prompt-based solutions as a tempting option in high-risk scenarios. **Reject them.**

---

## Multi-Concern Request Handling

When a customer reports multiple issues at once:

1. **Decompose** the request into separate concerns
2. Investigate each one **in parallel**, sharing context
3. Synthesize a single **unified resolution**

---

## Structured Handoff Protocols

Sometimes an agent can't resolve an issue and needs to escalate to a human agent. The critical rule for this escalation:

> **The human agent cannot access the conversation transcript.** The handoff summary must be self-contained.

A handoff summary needs to include:

- **Customer identity** (customer ID)
- **Conversation summary** — what happened, what the customer wants
- **Root cause analysis** — what's driving the issue
- **Refund amount** (if applicable)
- **Recommended action** — what the human agent should do next

---

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| Prompt-based guidance | Probabilistic — works most of the time, not a 100% guarantee |
| Programmatic enforcement | Deterministic — a prerequisite gate physically blocks the action, 100% guarantee |
| Decision rule | Financial / security / compliance → programmatic. Low risk → prompt is enough |
| Multi-concern requests | Decompose → investigate in parallel → synthesize a unified resolution |
| Handoff protocol | Self-contained summary: customer ID, summary, root cause, amount, recommended action |
| Exam trap | Prompt-based solutions get offered as an option in high-risk scenarios — reject them |

## Practice Scenario

> Production data shows that in 8% of cases, a customer support agent processes a refund without verifying account ownership. This has occasionally led to refunds being issued to the wrong account.
>
> **How do you fix this?**
>
> **A)** Add a programmatic prerequisite gate that requires the `verify_identity` tool to have completed successfully before the refund tool can run.
>
> **B)** Strengthen the system prompt: add the instruction "never process a refund without identity verification" and emphasize it in bold.
>
> **C)** Add few-shot examples — 3-4 example conversations showing the correct sequence.
>
> **D)** Add a routing classifier that routes refund requests to a verification flow first.

### Correct Answer: A

**Why A is correct:** This is a transaction with financial consequences — refunds are being issued to the wrong account. That requires a 100% guarantee. A programmatic prerequisite gate physically blocks the refund tool from running until `verify_identity` completes. Zero failure rate.

**Why B is wrong:** Strengthening the prompt is probabilistic — it might raise success from 92% to 97%, but it can't guarantee 100%. The current 8% failure rate is itself proof the prompt isn't sufficient. Financial risk remains.

**Why C is wrong:** Few-shot examples are also in the prompt-based-guidance category. They *guide* the model's behavior but don't *enforce* it. Same problem — not deterministic.

**Why D is wrong:** A routing classifier moves the problem elsewhere without solving it. The classifier itself can make mistakes. And the core issue remains: the refund tool can still be called without verification. No gate, no guarantee.
