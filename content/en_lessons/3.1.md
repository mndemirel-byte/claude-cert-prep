## Core Idea

When Claude Code starts, it looks for instruction files named `CLAUDE.md` that shape **how it behaves**. Coding standards, naming conventions, test requirements, project-specific context — all of it lives in these files. Think of them as a **persistent system prompt** for your codebase.

The critical point: **there are three levels**, and the exam repeatedly tests whether you know which level does what. The second critical point: CLAUDE.md is **context, not enforcement** — in the official wording, "Claude treats them as context, not enforced configuration." If an action must be blocked *every time, without exception*, the answer is not CLAUDE.md but a **hook** (see Domain 1.4 / 1.5).

---

## The Three Levels (The Ones the Exam Counts)

### 1. User level: `~/.claude/CLAUDE.md`

- Lives in your **home directory**
- Applies **only to YOU** — but in **EVERY project on your machine**
- **NOT under version control** — not in Git, not shared
- New teammates who clone the repo **do NOT receive** these instructions
- **Use for:** personal preferences that are project-independent (code style, personal shortcuts)
- **Trap:** if you put something project-specific here (a staging URL, test data) it **leaks into your other projects** — that belongs in `CLAUDE.local.md` (below)

### 2. Project level: `.claude/CLAUDE.md` or `CLAUDE.md` at the repo root

- Lives **in the repo**
- **Under version control** — tracked by Git, shared
- **EVERYONE** who clones the repo receives these instructions
- **Use for:** team-wide standards, build/test commands, API conventions, naming rules, architectural decisions

### 3. Directory level: `CLAUDE.md` files inside subdirectories

- Applied when Claude Code works on files **in that directory (and below it)**
- **Not loaded at launch** — loaded *on demand* when Claude reads a file in that subdirectory (lazy loading)
- **Use for:** package-specific rules (for example, `frontend/` has different rules than `backend/`)

### Two Locations the Exam Doesn't Count but You Should Know

| Location | What | Why it matters |
|---|---|---|
| `./CLAUDE.local.md` | At the project root, added to `.gitignore`: **personal + project-specific** (sandbox URLs, preferred test data) | The correct answer to the "personal but only in this project" scenario — not `~/.claude/CLAUDE.md` |
| Managed policy CLAUDE.md (`/etc/claude-code/CLAUDE.md`, macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`) | **Organization-wide** file deployed by IT/DevOps; cannot be disabled by individual settings | Where security/compliance rules live in a 40-developer org |

> **Exam rule:** The exam guide counts three levels → the answer to "how many levels?" is **three**. `CLAUDE.local.md` and managed policy appear as *distractors* or as the answer to a "most appropriate location" question.

## Summary Table

| Level | Location | Shared? | In Git? | For whom? | When loaded? |
|---|---|---|---|---|---|
| Managed | `/etc/claude-code/CLAUDE.md` etc. | ✅ (org) | ❌ (deployed via MDM) | Everyone on the machine | At launch, first |
| User | `~/.claude/CLAUDE.md` | ❌ No | ❌ No | Only you, all projects | At launch |
| Project | `.claude/CLAUDE.md` or root `CLAUDE.md` | ✅ Yes | ✅ Yes | Whole team | At launch |
| Local | `./CLAUDE.local.md` | ❌ No | ❌ (`.gitignore`) | Only you, this project | At launch, after the project file |
| Directory | `CLAUDE.md` in a subdirectory | ✅ Yes | ✅ Yes | Whoever works in that subtree | **On demand** (when a file there is read) |

## Loading Mechanism — "Which Level Wins?"

This is what the exam asks indirectly and most study material skips:

- Claude Code loads `CLAUDE.md` / `CLAUDE.local.md` from the working directory **and every directory above it** **at launch**. Start it in `foo/bar/` and both `foo/CLAUDE.md` and `foo/bar/CLAUDE.md` come in.
- Files in **subdirectories** are not loaded at launch; they are added when Claude reads a file in that directory.
- All discovered files are **concatenated** into context (from the filesystem root down to the working directory; at each level `CLAUDE.local.md` after `CLAUDE.md`). **No level overrides another.**
- Consequence: if two files hold **conflicting** rules, Claude may follow *either one*. The fix is not "set a priority" but **remove the conflict**.

> **Exam rule:** The option "the project CLAUDE.md overrides the user CLAUDE.md" is **wrong** — they are merged.

## Modular Organization

You don't have to cram everything into one giant `CLAUDE.md`. Two mechanisms exist:

### The `@path` Import Syntax (the exam calls it "@import syntax")

From inside `CLAUDE.md` you can reference external files with `@path/to/file`. **The word "import" is never written** — the `@` goes directly before the path, and it can sit inside a sentence:

```markdown
See @README for the project overview and @package.json for available npm commands.

# Standards
@docs/standards/api-conventions.md
@docs/standards/testing-rules.md

# Personal preferences (to share across git worktrees)
@~/.claude/my-project-instructions.md
```

Each package can import the standards relevant to it — clean and modular.

**Rules you need to know:**
- Relative paths resolve **relative to the file containing the import** (not the working directory)
- Imported files can import other files — up to **4 hops** deep
- An `@path` inside backticks or a code block is **not imported** (`` `@README` `` is plain text)
- Imports that resolve **outside** the working directory (`@~/...`) show an approval dialog the first time — protection against files others commit to a shared repo
- **Imports load at launch.** They do *not* save tokens; they only provide **organization**. The two mechanisms that do save tokens are subdirectory CLAUDE.md files and path-scoped rules (Task 3.3).

> **Exam rule:** The exam guide names this feature **"@import syntax"**. Recognize the term on the exam; write `@path` in code.

### The `.claude/rules/` Directory

Put topic-specific rule files here:

- `testing.md` — testing rules
- `api-conventions.md` — API rules
- `deployment.md` — deployment rules

Organized, topic-separated rules instead of one large file.

**Definition (same in 3.2 and 3.3):** `.claude/rules/*.md` files; if there is **no** `paths` frontmatter at the top, the file loads at launch every session with the same priority as `.claude/CLAUDE.md`; if there **is** one, it loads only while working with matching files (Task 3.3). `.md` files are discovered recursively in subfolders (`rules/frontend/`, `rules/backend/`). **Personal** rules can live in `~/.claude/rules/` (all projects). Shared rule sets can be linked in with symlinks.

## How to Write a Good CLAUDE.md (course module: "A CLAUDE.md That Follows")

- **`/init`** analyzes the codebase and generates a starter CLAUDE.md; if one exists it suggests improvements.
- **Size:** aim for **under 200 lines** per file. In a bloated CLAUDE.md Claude ignores half the rules — the most common answer to "the rule is written but not followed" is **pruning**.
- **Specificity:** not "Format code properly" but "2-space indentation"; not "Test your changes" but "Run `npm test` before committing".
- **Leave out:** anything Claude can infer from the code, standard language conventions, frequently changing information, file-by-file codebase descriptions. For each line ask: *"Would removing this cause Claude to make mistakes?"* If not, cut it.
- **Multi-step procedures** (migration steps) belong in a skill (Task 3.2), not CLAUDE.md; rules that apply **only to certain files** belong in a path-scoped rule (Task 3.3).
- Verify: run `/context` and confirm the file appears under **Memory files**.

## Debugging Tools: `/memory` and `/context`

If Claude Code behaves inconsistently across sessions, there are two commands:

| Command | What it does | Exam |
|---|---|---|
| `/memory` | **Lists and opens in your editor** the CLAUDE.md / CLAUDE.local.md locations at user and project scope; toggles auto memory | Exam guide: "verify which memory files are loaded and diagnose inconsistent behavior" → **the exam answer is `/memory`** |
| `/context` | Shows the CLAUDE.md and rules files **actually loaded in this session** under **Memory files** | The real diagnostic tool in practice |

To diagnose "works on my machine but not my teammate's": compare `/memory` (or `/context`) output on both machines — the difference is usually in `~/.claude/CLAUDE.md`.

## The Exam's Favorite Trap — The New Team Member Problem

This scenario shows up in almost every exam set:

> Developer A's Claude Code applies the team's naming conventions perfectly. Developer B, who joined last week, gets inconsistent names from Claude Code. Both work on the same repo.

**Root cause:** The rules are in Developer A's **user-level** configuration (`~/.claude/CLAUDE.md`). That file is not in Git and not shared. Developer B never receives the instructions.

**Fix:** Move the instructions to `.claude/CLAUDE.md` (project level) — version-controlled and shared.

> **Exam rule:** "New team member isn't getting the instructions" → the answer is almost always: **the instructions are at user level; move them to project level.**

---

## Key Takeaways for the Exam

| Concept | Remember |
|---|---|
| User level (`~/.claude/CLAUDE.md`) | Only you, **in every project** — not in Git, not shared |
| Project level (`.claude/CLAUDE.md`) | Applies to everyone — in Git, shared |
| Directory level (subdirectory `CLAUDE.md`) | While working in that subtree, loaded **on demand** |
| `CLAUDE.local.md` | Personal + project-specific, in `.gitignore` — the exam doesn't count it but it appears in options |
| Loading | Files are **concatenated**, none overrides another; conflict → Claude picks arbitrarily |
| `@path` ("@import syntax") | Reference external files — modular; **loads at launch**, no token savings |
| `.claude/rules/` | Topic-specific rule files; always loaded without `paths`, conditional with it |
| `/memory` | List/open memory files — the exam's "which files are loaded" answer |
| `/context` | Shows what actually loaded in this session |
| CLAUDE.md = context | Not enforcement; a rule with no exceptions → hook |
| 200 lines | Bloated file → rules get ignored → prune / split into rules / move to a skill |
| Exam trap | New member isn't getting instructions → instructions are at user level |

## Practice Scenario 1

> Developer A and Developer B both cloned the same repo. Developer A gets perfect API naming conventions from Claude Code. Developer B gets inconsistent names. Both work on the same branch.
>
> **What is the root cause?**
>
> **A)** Developer B's Claude Code version is outdated — it should be updated.
>
> **B)** The API naming conventions are in Developer A's user-level configuration (`~/.claude/CLAUDE.md`) — they should be moved to project level (`.claude/CLAUDE.md`).
>
> **C)** The Claude Code cache on Developer B's machine is corrupted — it should be cleared.
>
> **D)** Both developers should synchronize their memories with the `/memory` command.

### Correct Answer: B

**Why B is correct:** The classic exam trap. Developer A gets the instructions, Developer B doesn't, same repo — the only difference is Developer A's personal configuration. `~/.claude/CLAUDE.md` is not in Git and not shared. Fix: move it to `.claude/CLAUDE.md` so everyone gets it.

**Why A is wrong:** A version difference doesn't explain this kind of behavioral gap. Both developers can use the tool — the problem is missing instructions.

**Why C is wrong:** A cache problem doesn't explain instructions being entirely absent. The problem is structural — file location.

**Why D is wrong:** `/memory` is a diagnostic tool, not a sync tool. It shows memory files but doesn't copy someone else's.

## Practice Scenario 2

> A team works on a large project. The project root has a `.claude/CLAUDE.md` with general coding standards. But `frontend/` needs React-specific rules and `backend/` needs Go-specific rules. The team wants the React rules to take **no space at all** in context while working in the backend.
>
> **Which approach is correct?**
>
> **A)** Write all rules (general + React + Go) in a single root `.claude/CLAUDE.md`.
>
> **B)** Create directory-level files `frontend/CLAUDE.md` and `backend/CLAUDE.md` — Claude Code loads the relevant rules while working on files in that directory.
>
> **C)** From the root `.claude/CLAUDE.md`, import two files with `@docs/react-rules.md` and `@docs/go-rules.md`.
>
> **D)** Each developer writes the rules for their area in their own `~/.claude/CLAUDE.md`.

### Correct Answer: B

**Why B is correct:** Directory-level CLAUDE.md files exist for exactly this — different technology requirements in different subdirectories. `frontend/CLAUDE.md` holds the React rules, `backend/CLAUDE.md` the Go rules. Both are in Git, shared, and loaded **on demand only when files in that directory are read** — while working in the backend, the React rules never enter context.

**Why A is wrong:** Cramming everything into one file wastes tokens. Loading React rules while working in the backend pollutes context; the file also bloats and rules start being ignored.

**Why C is wrong:** The most tempting distractor. `@path` imports provide **organization**, but imported files load **at launch** together with the root CLAUDE.md — the React rules would still be in context while working in the backend. Since the requirement is "no space at all", imports are insufficient. (If the requirement were only "don't let one file bloat", C would be acceptable.)

**Why D is wrong:** User-level configuration isn't shared and leaks into every project. New team members don't get the rules; no standardization.

## Practice Scenario 3

> A developer wants Claude Code to know the project's staging URL and their own test-account details in every session. This information is personal — it must not be shared with the team or committed to the repo. But the developer also wants it **absent** from context when working on other projects.
>
> **Where should it go?**
>
> **A)** `~/.claude/CLAUDE.md` — personal, not shared.
>
> **B)** `.claude/CLAUDE.md` — project level, loaded every session.
>
> **C)** `CLAUDE.local.md` at the project root — added to `.gitignore`.
>
> **D)** `.claude/rules/staging.md` — a topic-specific rule file.

### Correct Answer: C

**Why C is correct:** Two constraints: personal (must not enter the repo) **and** project-specific (must not leak into other projects). `CLAUDE.local.md` is designed for exactly that intersection — it sits at the project root, loads alongside `CLAUDE.md`, and goes into `.gitignore`.

**Why A is wrong:** `~/.claude/CLAUDE.md` is personal but loads in **every project** on the machine — the staging URL would be in context in another project, and Claude might even try to use it there.

**Why B is wrong:** A project-level file goes into Git; personal account details would be shared with the team.

**Why D is wrong:** `.claude/rules/` is project scope and goes into Git; and this is personal context, not a "rule".
