## The Core Idea

When Claude Code runs, it looks for instruction files called `CLAUDE.md` that determine **how it behaves**. Coding standards, naming conventions, test requirements, project-specific context — all defined in these files. Think of it as a **persistent system prompt** for your codebase.

The critical point: **there are three levels**, and the exam constantly tests whether you know which level does what.

---

## The Three Levels

### 1. User Level: `~/.claude/CLAUDE.md`

- Lives in your **home directory**
- Applies **ONLY to YOU**
- **NOT under version control** — not in Git, not shared
- New teammates who clone the repo **DO NOT** get these instructions
- **Use case:** personal preferences, personal shortcuts

### 2. Project Level: `.claude/CLAUDE.md` or `CLAUDE.md` in the root

- Lives **in the repo**
- **Under version control** — tracked by Git, shared
- **EVERYONE** who clones the repo gets these instructions
- **Use case:** team-wide standards, API conventions, naming rules

### 3. Directory Level: `CLAUDE.md` files inside subdirectories

- Applied when Claude Code works on **files in that directory**
- **Use case:** package-specific rules (e.g. the frontend folder has different rules from the backend)

---

## Summary Table

| Level | Location | Shared? | In Git? | For whom? |
|---|---|---|---|---|
| User | `~/.claude/CLAUDE.md` | ❌ No | ❌ No | Only you |
| Project | `.claude/CLAUDE.md` or root `CLAUDE.md` | ✅ Yes | ✅ Yes | Whole team |
| Directory | `CLAUDE.md` in a subdirectory | ✅ Yes | ✅ Yes | Whoever works in that directory |

## Modular Organisation

You don't have to cram everything into one giant `CLAUDE.md`. There are two mechanisms:

### The `@import` Syntax

You can reference external files from inside `CLAUDE.md`:

```markdown
@import ./standards/api-conventions.md
@import ./standards/testing-rules.md
```

You can import the relevant standards per package — clean and modular.

### The `.claude/rules/` Directory

Put topic-specific rule files in this directory:

- `testing.md` — test rules
- `api-conventions.md` — API rules
- `deployment.md` — deployment rules

Organised, topic-separated rules instead of one big file.

---

## Debugging Tool: The `/memory` Command

If Claude Code behaves inconsistently across sessions, use the `/memory` command to verify **which memory files are loaded**.

This is how you diagnose "works for me but not for my teammate" problems.

---

## The Exam's Favourite Trap — The New Team Member Problem

This scenario shows up in almost every exam set:

> Developer A's Claude Code applies the team's naming conventions perfectly. Developer B, who joined last week, gets inconsistent names from Claude Code. Both work on the same repo.

**Root cause:** the rules are in Developer A's **user-level** configuration (`~/.claude/CLAUDE.md`). That file is not in Git, not shared. Developer B never receives those instructions.

**Fix:** move the instructions to `.claude/CLAUDE.md` (project level) — version-controlled and shared.

> **Exam rule:** "The new team member doesn't get the instructions" → the answer is almost always: **the instructions are at user level and must move to project level.**

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| User level (`~/.claude/CLAUDE.md`) | Applies only to you — not in Git, not shared |
| Project level (`.claude/CLAUDE.md`) | Applies to everyone — in Git, shared |
| Directory level (`CLAUDE.md` in a subdirectory) | Applied when working in that directory |
| `@import` syntax | Reference external files from CLAUDE.md — modular organisation |
| `.claude/rules/` | Topic-specific rule files — instead of one big file |

## Practice Scenario 1

> Developer A and Developer B both cloned the same repo. Developer A gets perfect API naming conventions from Claude Code. Developer B gets inconsistent names. Both work on the same branch.
>
> **What is the root cause?**
>
> **A)** Developer B's Claude Code version is old — it should be updated.
>
> **B)** The API naming rules are in Developer A's user-level configuration (`~/.claude/CLAUDE.md`) — they should move to project level (`.claude/CLAUDE.md`).
>
> **C)** The Claude Code cache on Developer B's machine is corrupted — it should be cleared.
>
> **D)** Both developers should synchronise their memories with the `/memory` command.

### Correct Answer: B

**Why B is correct:** the classic exam trap. Developer A gets the instructions, Developer B doesn't, same repo — the only difference is Developer A's personal configuration. `~/.claude/CLAUDE.md` is not in Git, not shared. Fix: move it to `.claude/CLAUDE.md` so everyone gets it.

**Why A is wrong:** a version difference does not explain this kind of behavioural difference. Both developers can use the tool — the problem is the missing instructions.

**Why C is wrong:** a cache problem does not explain instructions being entirely absent. The problem is structural — the file's location.

**Why D is wrong:** `/memory` is a diagnostic tool, not a synchronisation tool. It shows the memory files; it does not copy someone else's files.

## Practice Scenario 2

> A team works on a large project. The project root has a `.claude/CLAUDE.md` with general coding standards. But the `frontend/` folder needs React-specific rules and the `backend/` folder needs Go-specific rules.
>
> **What is the right approach?**
>
> **A)** Write all rules (general + React + Go) into the single root `.claude/CLAUDE.md`.
>
> **B)** Create directory-level `frontend/CLAUDE.md` and `backend/CLAUDE.md` files — Claude Code applies the relevant rules when working on files in that directory.
>
> **C)** Each developer writes the rules for their area in their own `~/.claude/CLAUDE.md`.
>
> **D)** Add the React and Go rules to the system prompt.

### Correct Answer: B

**Why B is correct:** directory-level CLAUDE.md files exist exactly for this — different technology requirements in different subdirectories. `frontend/CLAUDE.md` holds the React rules, `backend/CLAUDE.md` the Go rules. Both files are in Git, shared, and only loaded when working in the relevant directory.

**Why A is wrong:** cramming all rules into one file wastes tokens. Loading React rules while working in the backend is pointless — it pollutes the context.

**Why C is wrong:** user-level configuration is not shared. New team members don't get the rules. It also depends on personal preference — no standardisation.

**Why D is wrong:** the system prompt is a different mechanism. Directory-level CLAUDE.md files solve this correctly and cleanly.
