## The Core Idea

When steering a Claude agent for tasks like code review, security scanning or document analysis, the most common mistake is: **giving vague, subjective instructions.**

> *"Only report important findings."*
> *"Be conservative when you're not confident."*
> *"Only flag high-confidence issues."*

These instructions **don't work.** Claude has no reason to understand "important" or "high confidence" the way you mean them.

The right approach: **categorical, concrete criteria.** Tell Claude **what to do**, not "what to feel".

---

## Vague vs Explicit Criteria — Side by Side

### ❌ Vague (Wrong Answer on the Exam)

```
"Only report high-confidence findings. When unsure, prefer to be
conservative. Skip trivial issues."
```

**Why it fails:**
- "High confidence" is not a numeric threshold; Claude sets a different bar every time
- "Trivial" is subjective; Claude has no access to the business context
- Vague instructions produce **inconsistent output** — same code, different findings on different runs

### ✅ Explicit (Right Answer on the Exam)

```
"Flag only the following:
- The claimed behaviour contradicts the actual code behaviour
- A security vulnerability exists (injection, auth bypass, plain data leak)
- A clear logic error exists (wrong loop condition, null pointer risk)

SKIP the following:
- Minor style preferences (whitespace, naming conventions)
- Team-local idioms
- Performance suggestions (unless a critical bottleneck)"
```

**Why it works:**
- Each rule is a **decision-tree node** — Claude either flags or skips, no interpretation
- The same code produces **consistent results** every time
- There is no grey zone requiring human review

## The False-Positive Trust Problem — The Exam's Favourite Trap

Understand this well: **the exam tries to trip you here.**

### Scenario

You have a code review agent in a CI/CD pipeline. It reports three categories:
- **Security vulnerabilities** → 95% accuracy
- **Logic errors** → 90% accuracy
- **Documentation gaps** → 40% accuracy (lots of false alarms)

Developers noticed half the "documentation gap" findings are nonsense. What happens next?

**The real problem:** developers now **distrust the security findings too.** Once one category loses trust, the whole agent's output looks unreliable.

### The Wrong Answers the Exam Offers

- *"Make all categories more conservative"* — no, that misses real problems
- *"Raise the confidence threshold for the documentation category"* — vague, doesn't work
- *"Retrain the agent completely"* — disproportionate, slow

### ✅ The Right Fix

**Temporarily disable the high-false-positive category**, preserve trust in the other categories while you improve that category's prompt.

```
Steps:
1. Remove the "documentation gaps" category from the pipeline
2. Security and logic categories keep running normally
3. Write new, explicit criteria for documentation (as below)
4. Test on a small dataset → re-add once the false-positive rate is acceptable
```

**Core principle:** the fastest way to regain trust is to isolate the badly performing component.

## Severity Calibration — With Code Examples

The exam also tries to trip you here: when it says *"define severity levels"* it offers you answers with **prose descriptions**.

The right answer always contains **real code examples**.

### ❌ Wrong Calibration (Prose)

```
"Critical: issues that could crash the system or leak data.
Major: bugs affecting important functionality.
Minor: small issues."
```

**Why it fails:** Claude's definition of "could crash the system" may not match yours.

### ✅ Right Calibration (Code Examples)

```python
# CRITICAL — always report:
def get_user(user_id):
    query = f"SELECT * FROM users WHERE id = {user_id}"  # SQL injection
    # → Directly exposed to a database attack

password = "admin123"  # Hard-coded credential in code
# → Credential leak

# MAJOR — report:
def calculate_total(items):
    total = 0
    for i in range(len(items) + 1):  # Off-by-one error
        total += items[i]

# MINOR — skip:
def getUserData():  # Should be snake_case, not camelCase
    pass  # Style only; doesn't affect functionality
```

**Why it works:** Claude no longer interprets — it checks "does this look like that code?"

## Key Takeaways

| # | Key takeaway |
|---|---|
| 1 | **Vague instructions → inconsistent output.** "Be conservative" is a wish, not an instruction. |
| 2 | **Explicit criteria = decision tree.** Every rule resolves to "flag" or "skip". |
| 3 | **Lost trust in one category affects the whole agent.** Trust is holistic, not per category. |
| 4 | **Fix: disable the problematic category**, improve it, re-add it. Don't slow the whole system. |
| 5 | **Use real code examples, not prose, for severity calibration.** |
| 6 | **In a CI/CD context a false positive is less harmful than a false negative** — but both are minimised with good criteria. |

## Practice Questions with Explanations

### Question 1

A security scanning agent sometimes fails to report real vulnerabilities and sometimes raises trivial warnings. The developer writes: *"Only report real security issues; skip if unsure."* Is this sufficient?

**A)** Yes, "real security issue" is clear enough for Claude
**B)** No, "real" and "if unsure" are subjective; categorical criteria are needed
**C)** No, but adding a confidence-threshold parameter solves it
**D)** Yes, Claude calibrates well in the security domain

**✅ Answer: B**

*Explanation:* "Real security issue" and "if unsure" are subjective. Claude can set a different bar on every run. The right approach: categorical criteria such as "SQL injection, hard-coded credentials, authentication bypass — report these. Deprecation warnings, performance suggestions — skip these."

---

### Question 2

A pipeline has three analysis categories: security (92% accuracy), performance (88%), code style (35%). Developers are starting to lose trust in the security findings. What is the best action?

**A)** Raise all categories' thresholds above 90%
**B)** Temporarily disable the code-style category, keep the others running
**C)** Replace the agent with a bigger model
**D)** Collect more sample data for all three categories

**✅ Answer: B**

*Explanation:* the problem is the code-style category poisoning trust. The fix is isolation: remove the bad category, let the good ones keep running. Raising thresholds (A) misses real problems. Changing the model (C) is disproportionate. More data (D) doesn't fix the root cause — the problem is the prompt criteria.

---

### Question 3

Which is the most effective definition of severity levels?

**A)** "Critical: issues threatening system security. Major: bugs breaking important functionality."
**B)** A scheme showing each level with concrete code examples: "Critical: injection patterns such as `query = f"SELECT * FROM users WHERE id = {user_id}"`"
**C)** A percentage confidence threshold per level: "Critical: 95%+, Major: 80–95%"
**D)** General descriptions compiled from developers' past review notes

**✅ Answer: B**

*Explanation:* prose descriptions (A) are open to interpretation. Confidence thresholds (C) give inconsistent calibration. Past notes (D) are unstructured. Real code examples make Claude ask "does this look like that code?" — no interpretation, pattern matching.

---

### Question 4

An agent is given the instruction: *"Only report high-priority issues."* What problem arises?

**A)** The agent doesn't run; "high priority" isn't a valid parameter
**B)** The agent reports everything and doesn't filter
**C)** Because "high priority" is subjective, results are inconsistent across runs
**D)** The agent returns an incorrect error message

**✅ Answer: C**

*Explanation:* Claude runs and filters, but sets the "high priority" threshold differently every time. The same codebase can yield different findings. Inconsistency is the real cost of vague criteria.
