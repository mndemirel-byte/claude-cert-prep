## The Core Idea

You're running a structured data extraction pipeline. The model extracts fields from invoices, reads dates from contracts, pulls amounts from documents. The system reports 97% overall accuracy. Everything looks fine — until you discover a 40% error rate on one specific document type.

This task statement teaches how aggregate metrics can mislead, confidence calibration, and how to optimise human review capacity.

---

## The Aggregate Metrics Trap

### Problem

**97% accuracy** system-wide looks great. But that figure is the average across all document types:

| Document type | Volume | Accuracy |
|---|---|---|
| Standard invoices | 70% | 99.5% |
| Contracts | 20% | 98% |
| Handwritten notes | 10% | 60% |

Handwritten notes are only 10% of the total volume but have a **40% error rate**. That error is masked by the 99.5% accuracy of the high-volume standard invoices.

### Fix

Before moving to automation, validate accuracy along **two dimensions**:

1. **By document type:** calculate a separate accuracy rate per document type
2. **By field segment:** calculate a separate accuracy rate per extracted field

```
Accuracy Analysis:
├── By document type:
│   ├── Standard invoices: 99.5% ✅ Suitable for automation
│   ├── Contracts: 98% ✅ Suitable for automation
│   └── Handwritten notes: 60% ❌ Human review required
│
└── By field segment:
    ├── Total amount: 99% ✅
    ├── Date: 97% ✅
    ├── Tax ID: 94% ⚠️ Monitor
    └── Payment terms: 78% ❌ Human review required
```

**Rule:** 97% overall accuracy can hide a 40% error rate on a specific document type. Before moving to automation, always validate by document type AND by field segment.

## Stratified Random Sampling

### Problem

The system runs with high confidence — 95% of extractions come back with a high confidence score. But when a new document format appears (e.g. a new supplier's invoice template) the model can produce **wrong** extractions with high confidence.

These "novel error patterns" can't be detected with the existing confidence thresholds.

### Fix

Regularly take random samples even from high-confidence extractions and verify them with humans:

```
Every week:
├── Low-confidence extractions: 100% human review (already done)
├── Medium-confidence extractions: 30% sampling
└── High-confidence extractions: 5% sampling ← THIS IS CRITICAL
```

**Why sample high-confidence extractions too?**

- The model can be wrong with high confidence on new document formats (uncalibrated confidence)
- Slowly changing document formats (drift) can invalidate the confidence thresholds
- Reviewing only the low-confidence ones misses novel error patterns

## Field-Level Confidence Calibration

### Concept

The model gives a separate confidence score for each extracted field:

```json
{
  "invoice_number": {"value": "INV-2024-001", "confidence": 0.99},
  "total_amount": {"value": 1547.83, "confidence": 0.95},
  "tax_id": {"value": "TR1234567890", "confidence": 0.72},
  "payment_terms": {"value": "Net 30", "confidence": 0.45}
}
```

### Calibration Process

1. **Build labelled validation sets (ground truth data):** a test set of documents whose true values are known
2. **Calibrate the confidence thresholds:** in fields where the model says 90% confidence, is there really 90% accuracy?
3. **Set up threshold-based routing:**

```
if confidence >= 0.90: → automatic acceptance
if 0.70 <= confidence < 0.90: → add to the human review queue
if confidence < 0.70: → priority human review
```

### Review Capacity Optimisation

Human review capacity is limited — if 200 documents a day can be reviewed, how do you use that capacity most effectively?

**Rule:** prioritise the limited review capacity for the highest-uncertainty items.

```
Prioritisation:
1. Low-confidence fields (confidence < 0.70) → REVIEW FIRST
2. Medium-confidence fields (0.70–0.90) → SECOND
3. High-confidence sampling (5%) → LAST (but NOT skipped)
```

With this approach:
- The riskiest extractions are reviewed first
- Limited human capacity is directed at the highest-impact areas
- High-confidence sampling detects novel error patterns

---

## Calibration vs Confidence Score — A Critical Distinction

**Raw confidence score:** the model's own assessment. Without calibration it can be unreliable (remember the model confidence score trap in Task 5.2).

**Calibrated confidence:** thresholds verified and adjusted with labelled validation sets. When the model says "90% confident" there really is 90% accuracy.

**Exam note:** in Task 5.2 we said "the model confidence score is unreliable as an escalation trigger". Here we say "route to human review with field-level confidence calibration". What's the difference?

- **5.2:** a raw, uncalibrated confidence score → unreliable for the escalation decision
- **5.5:** confidence thresholds calibrated with labelled data → reliable for review routing

The key difference: **calibration**. A raw confidence score is unreliable; a calibrated one is usable.

## Practice Scenario 1

> A document extraction system reports 97% overall accuracy. Management plans to move the system to full automation — removing all human review.
>
> Internal audit finds a 40% error rate on extractions from handwritten notes.
>
> **What is the right approach?**
>
> **A)** 97% overall accuracy is enough — move to full automation.
>
> **B)** Keep human review for all document types — even 97% is unreliable.
>
> **C)** Evaluate accuracy separately by document type and field segment. Automate the high-accuracy types, keep the low-accuracy types (handwritten notes) in human review.
>
> **D)** Remove handwritten notes from the pipeline entirely — problem solved.

### Correct Answer: C

**Why C is correct:** avoids the aggregate metrics trap. Evaluates accuracy separately by document type and field segment. Standard invoices (99.5%) are suitable for automation, handwritten notes (60%) need human review. Evaluate each type on its own performance.

**Why A is wrong:** the aggregate metrics trap. 97% overall accuracy hides the 40% error rate on handwritten notes. Full automation causes serious errors on that document type.

**Why B is wrong:** human review for all types is a needless resource cost. For standard invoices at 99.5% accuracy, human review adds no value.

**Why D is wrong:** removing handwritten notes is data loss. The right fix is routing that type to human review, not removing it from the pipeline.

## Practice Scenario 2

> An extraction system gives field-level confidence scores. The system designer applied this rule: "If the confidence score is above 80%, accept automatically."
>
> The 80% threshold was set intuitively, without any validation data.
>
> Analysis of the last 1,000 documents shows: in fields where the model says 85% confidence, the real accuracy is 62%.
>
> **What are the root cause and the fix?**
>
> **A)** Raise the threshold to 95% — be more conservative.
>
> **B)** The confidence thresholds weren't calibrated with labelled validation sets (ground truth data). The model's 85% confidence corresponds to 62% real accuracy. Fix: calibrate the thresholds with labelled data.
>
> **C)** Use a bigger model — the confidence scores will be more accurate.
>
> **D)** Remove the confidence score entirely — it doesn't work.

### Correct Answer: B

**Why B is correct:** the raw confidence score isn't calibrated. The model says 85% but real accuracy is 62% — a serious calibration gap. Fix: calibrate the thresholds with labelled validation sets. Once you know the model's 85% actually corresponds to 62%, you adjust your threshold accordingly.

**Why A is wrong:** raising the threshold doesn't fix the calibration problem. At 95% the model's confidence may still be misaligned with real accuracy. Data-based calibration is needed instead of an intuitive threshold.

**Why C is wrong:** a bigger model doesn't guarantee confidence calibration. Calibration is a process independent of model size — it must be done separately for every model.

**Why D is wrong:** once calibrated, the confidence score is a very valuable tool. Removing the tool instead of fixing the problem is wrong. A calibrated confidence score optimises human review routing.
