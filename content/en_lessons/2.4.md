## The Core Idea

MCP (Model Context Protocol) is the protocol that lets Claude connect to external tools and data sources. This task statement teaches how MCP servers are configured, scoped, and when a custom server should be built.

---

## Scoping Hierarchy

There are two levels:

### 1. Project Level: `.mcp.json`
- Lives in the project repository
- **Under version control** — tracked by Git
- Shared with the team
- Everyone on the team uses the same tool configuration

### 2. User Level: `~/.claude.json`
- Lives in the user's home directory
- **Personal** — NOT under version control
- Not shared with the team
- For personal tool preferences and credentials

### Important Detail
Tools from all configured servers are **discovered at connection time** and are available simultaneously.

---

## Environment Variable Expansion

`.mcp.json` supports the `${VARIABLE_NAME}` syntax. This keeps credentials out of version control.

```json
{
  "mcpServers": {
    "github": {
      "command": "github-mcp-server",
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
```

**Advantage:** each developer sets their own token locally. Tokens never enter the repo. Security is preserved.

---

## MCP Resources

MCP servers can expose not just tools but **resources**:

- Issue summaries
- Documentation hierarchies
- Database schemas

**Benefit:** they show agents a catalogue of the available data — no exploratory tool calls needed. Fewer unnecessary queries.

Example: an agent sees the database schema as an MCP resource and knows which tables exist — it queries the right table directly instead of probing at random.

---

## The Build vs Use Decision

This decision is tested. The rule is clear:

### Evaluate Community MCP Servers First
For standard integrations (Jira, GitHub, Slack, databases) **community MCP servers** already exist. Use them.

### When to Build a Custom Server?
**Only** when team-specific workflows cannot be covered by community servers.

Examples:
- A connection to the company's proprietary internal API is needed → custom server required
- A standard Jira integration is needed → community server suffices

### Enriching MCP Tool Descriptions

An important detail: an agent may sometimes prefer built-in tools (like Grep) over MCP tools. The cause may be an inadequate MCP tool description. **Enrich the MCP tool descriptions** so the agent picks the right tool.

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| `.mcp.json` | Project level — under version control, shared with the team |
| `~/.claude.json` | User level — personal, not shared |
| Environment variables | `${GITHUB_TOKEN}` syntax — keeps credentials out of the repo |
| MCP resources | Expose content catalogues — fewer exploratory queries |
| Build vs use | Standard integration → community server. Custom workflow → custom server |
| Description enrichment | Improve MCP tool descriptions so the agent does not prefer built-in tools |

## Practice Scenario

> A team wants to set up a Jira integration. A developer proposes building a custom MCP server — it will connect to the Jira API, create issues, update statuses and fetch sprint information.
>
> **Is this the right approach?**
>
> **A)** Yes — a custom server fits the team's needs exactly and gives full control.
>
> **B)** No — evaluate the community Jira MCP server first. Standard issue creation, status updates and sprint retrieval are already covered by the community server. Build a custom server only if there are team-specific custom workflows.
>
> **C)** No — use Jira's own API directly, MCP is not needed.
>
> **D)** Yes — but first set up the GitHub MCP server, then build the Jira server on top of it.

### Correct Answer: B

**Why B is correct:** Standard Jira operations (issue creation, status updates, sprint info) are already covered by community MCP servers. Building a custom server is wasted effort — maintenance cost, testing cost, update cost. Consider a custom server only when the community server is insufficient (a team-specific workflow).

**Why A is wrong:** "Full control" sounds good, but building from scratch when an existing solution exists is over-engineering. Exam principle: the simple, low-effort fix first.

**Why C is wrong:** The MCP layer is the standard protocol that lets Claude discover and use tools. Direct API use does not fit the agent architecture.

**Why D is wrong:** GitHub and Jira are independent integrations — building one on top of the other makes no sense.
