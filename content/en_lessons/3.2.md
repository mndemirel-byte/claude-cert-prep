## The Core Idea

In Claude Code you can define repeated workflows as **custom commands** and **skills**. They are invoked with slash commands such as `/review`, `/test-setup`, `/brainstorm`. The exam expects you to know **where to put them**, **how to configure them** and **how they differ from CLAUDE.md**.

---

## Directory Structure

### Project-Scoped Commands (Shared)

```
.claude/commands/
```

- Lives in the project repository
- **Under version control** — shared via Git
- Everyone on the team can use them
- Example: `/review`, `/deploy-checklist`, `/test-all`

### Personal Commands (Not Shared)

```
~/.claude/commands/
```

- Lives in the user's home directory
- **Not shared** — only you use them
- Does not affect teammates
- Example: a personal `/brainstorm`, `/quick-fix`

### Skill Files

```
.claude/skills/
```

- Contains `SKILL.md` files
- **Invoked on demand**
- Configurable through frontmatter options

---

## Skill Frontmatter Options

You can configure a skill's behaviour with YAML frontmatter at the top of the file. Three critical options:

### 1. `context: fork` — Isolated Sub-Agent Context

```yaml
---
context: fork
---
```

- Runs the skill in an **isolated sub-agent** context
- Detailed/noisy output stays in that isolated context
- **The main conversation stays clean** — only a summary returns
- **Use case:** codebase analysis, brainstorming, exploration tasks — anything that produces a lot of output

### 2. `allowed-tools` — Tool Restriction

```yaml
---
allowed-tools:
  - Read
  - Grep
  - Glob
---
```

- **Restricts** which tools the skill may use
- **Prevents destructive actions** during the skill's execution
- For example, an analysis skill should not be able to write or delete files

### 3. `argument-hint` — Parameter Hint

```yaml
---
argument-hint: "Enter the path of the file to analyse"
---
```

- Tells the developer what to enter when the skill is invoked **without arguments**
- Improves the user experience

## Critical Distinction: Skill vs CLAUDE.md

The exam tests this distinction directly. Don't mix them up.

| Property | CLAUDE.md | Skill |
|---|---|---|
| Loading | **Always loaded** — automatic | **On demand** — when invoked |
| Purpose | Universal standards | Task-specific workflows |
| Example | "All functions must be documented with JSDoc" | "/review — review the PR" |
| Rule | Put universal standards here | Put task-specific procedures here |

> **Don't put task-specific procedures in CLAUDE.md. Don't put universal standards in skills.**

- ✅ CLAUDE.md → "All API endpoints must use camelCase naming"
- ✅ Skill → "/migrate — generate a database migration script"
- ❌ CLAUDE.md → "When doing a migration follow these steps" (task-specific — should be a skill)
- ❌ Skill → "Always use TypeScript strict mode" (universal — should be CLAUDE.md)

---

## Personal Skill Customisation

If you want personal variants of team skills:

1. Put them in `~/.claude/skills/` (personal, not shared)
2. Use a **different name** — so they don't clash with team skills
3. Customise your personal workflow without affecting teammates

---

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| `.claude/commands/` | Project-scoped — in Git, shared with the team |
| `~/.claude/commands/` | Personal — not shared |
| `.claude/skills/` + `SKILL.md` | On-demand workflows |
| `context: fork` | Isolated sub-agent — detailed output stays there, main conversation clean |
| `allowed-tools` | Restricts the tools a skill may use — prevents destructive actions |
| `argument-hint` | Shows a parameter hint when invoked without arguments |
| Skill vs CLAUDE.md | Skill = task-specific, on demand. CLAUDE.md = universal, always loaded |
| Personal skills | `~/.claude/skills/` — with a different name, without affecting the team |

## Practice Scenario 1

> A team wants two things:
> 1. A `/review` command everyone will use — to review PRs
> 2. One developer wants a personal `/brainstorm` skill — it produces very detailed output and must not pollute the main conversation
>
> **Where should each go and how should it be configured?**
>
> **A)** Both go in `.claude/commands/` — for team sharing.
>
> **B)** `/review` → `.claude/commands/` (project-scoped, shared). `/brainstorm` → a `SKILL.md` in `~/.claude/skills/` with the `context: fork` frontmatter (personal, runs in an isolated context).
>
> **C)** Both should be written as instructions in CLAUDE.md.
>
> **D)** Both go in `~/.claude/commands/` — a matter of personal preference.

### Correct Answer: B

**Why B is correct:** two different requirements, two different solutions:
- `/review` is a command everyone uses → `.claude/commands/` (project-scoped, in Git, shared)
- `/brainstorm` is personal and produces detailed output → `~/.claude/skills/` (personal, not shared) + `context: fork` (isolated context, main conversation stays clean)

**Why A is wrong:** `/brainstorm` is a personal request — putting it in team commands affects everyone. It also needs the `context: fork` configuration, and that frontmatter support does not work in the commands directory the way it does for skills.

**Why C is wrong:** these are task-specific procedures — CLAUDE.md is for universal standards. CLAUDE.md is also always loaded, with no on-demand invocation mechanism.

**Why D is wrong:** `/review` must be team-wide — putting it in the personal directory means other team members can't access it. New members won't get the command.

## Practice Scenario 2

> A team's `.claude/CLAUDE.md` contains this instruction:
>
> ```
> When doing a database migration:
> 1. Back up the current schema first
> 2. Generate the migration script
> 3. Run it in the test environment
> 4. Verify the results
> ```
>
> Claude Code loads these instructions in every conversation — even when no migration is being done.
>
> **What is the problem?**
>
> **A)** The CLAUDE.md file is too long — it should be shortened.
>
> **B)** A task-specific procedure (migration steps) is in CLAUDE.md — it should be a skill, invoked on demand.
>
> **C)** The instructions should be in English — Claude misinterprets non-English instructions.
>
> **D)** It should move to the `.claude/rules/` directory instead of CLAUDE.md.

### Correct Answer: B

**Why B is correct:** the migration procedure is a task-specific workflow — not needed in every conversation. CLAUDE.md is always loaded, which means needless token consumption and context pollution every time. The right place: define it as a skill file in `.claude/skills/`, invoked only when a migration is needed.

**Why A is wrong:** the file's length is not the real problem — the problem is a task-specific procedure living in an always-loaded file.

**Why C is wrong:** not a language issue. Claude handles instructions in any language well. The problem is structural — the content's location.

**Why D is wrong:** the `.claude/rules/` directory is for path-based rules (covered in Task 3.3). The migration procedure is tied to a task, not to a file path — it should be a skill.
