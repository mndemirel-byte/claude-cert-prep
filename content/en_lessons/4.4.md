## Core Idea

The first extraction is not always perfect. Validation-retry asks the question: **"Can the error be sent back and can the model correct itself?"**

The answer depends on the situation. And the exam tests exactly whether you know this distinction.

**Retry's domain:** As you saw in Task 4.3, tool_use (especially `strict: true`) reduces schema-syntax errors to zero. The remaining errors are **semantic** — the total does not add up, the value is in the wrong field, the format is not as expected. The exam guide's distinction: "*semantic validation errors (values don't sum, wrong field placement) vs schema syntax errors (eliminated by tool use)*". The retry loop exists only for the first group.

---

## Retry-with-Error-Feedback Architecture

### Basic Flow

```
1. Document is sent → First extraction is received (tool_use)
2. Extraction is validated (schema/type + semantic rules)
3. If there is an error → Sent back to the model together with the error message
4. Model sees the original document + the failed extraction + the error
5. Model corrects itself → New extraction
6. Validate again
```

### Contents of the Retry Request

The exam guide's Skills item: "*follow-up requests that include **the original document, the failed extraction, and specific validation errors***". All three are needed:

```
Original document:         {original_document}
Your first extraction:     {failed_extraction}
Validation error:          {validation_error}   ← field name + expected + found
Please correct the extraction taking the error into account.
```

**Critical:** Just telling the model "try again" is not enough. A **specific, model-readable error message** is needed — which field, what was expected, what came back. The model cannot fix what it does not know it got wrong.

**Natural form:** When you use tool_use, the retry is not a separate prompt but a **multi-turn conversation**: the assistant's `tool_use` block stays in the history, you send the error message inside a `tool_result`, and the model calls the same tool again with a corrected `input` (the course's *Sending tool results* lesson).

## Cases Where Retry Is Effective

Memorize these — the exam asks "does retry work for this scenario?"

### ✅ Effective: Format Mismatches

```
Error: "invoice_date field is in '15/01/2024' format, expected: 'YYYY-MM-DD'"
Fix: The model returns "2024-01-15" again.

Why it works: The information IS in the document, it is just formatted wrong.
```

### ✅ Effective: Structural Output Errors

```
Error: "line_items array has 3 items but the total line count was entered as 2"
Fix: The model corrects the line count to 3.

Why it works: The contradiction is detectable; the model can look again and fix it.
```

### ✅ Effective: Placement in the Wrong Field

```
Error: "The total value appears in the unit_price field ($450, 3 units × $150)"
Fix: The model corrects unit_price to 150 and total to 450.

Why it works: Both values exist in the source document, only the fields got mixed up.
```

---

## Cases Where Retry Is NOT Effective — The Exam's Trap

### ❌ Not Effective: The Information Genuinely Is Not in the Source

```
Error: "discount_rate null — required field"
Reality: No discount rate is written anywhere in the document.

What the model does: Even if it retries, it will look at the same document.
If the information is not there, the model fabricates or returns null again.

Correct solution: Make discount_rate nullable in the schema.
```

### ❌ Not Effective (but a different solution): The Information Is in an External Document

The exam guide's own example: "*information exists only in an **external document not provided***" — payment terms are in the framework agreement, the discount rate in the previous invoice, the unit price in the price list.

```
Error: "payment_terms null"
Reality: The invoice says "payment terms: see contract No. 2024-17".

What the model does: Retry → null again (it does not have the contract).

Correct solution: NOT nullable — add the missing document to the context
(send the contract too), THEN retry. Retry only works when the information
is in the context.
```

Diagnostic hint: the model returns null **and** the document references another document → not "no document", but "missing document". The answer to the first is nullable, the answer to the second is context.

### ❌ Not Effective: Inconsistent Source Document

```
Document content:
- Line items: 300 + 450 + 200 = $950
- Cover page total: $1,100

Retry error message: "Line items sum to 950, stated total $1,100"

What the model does: Which one is correct? The document contradicts itself.
Retry does not help — the model cannot choose for the document.

Correct solution: Add a conflict_detected flag, route to human review.
```

### Diagnostic table

| Symptom | Where is the information? | Retry? | Correct tool |
|---------|---------------|--------|------------|
| Wrong format / wrong field / count error | In the document | ✅ | Retry with error message |
| Null, not in the document at all | Nowhere | ❌ | Nullable field (4.3) |
| Null, document references another document | In an external document | ❌ (first) | Add the document → then retry |
| Null, information is in the document but in a different format | In the document | ⚠️ partially | Few-shot (4.2) — retry makes the same mistake every time |
| Two values conflict | Document is inconsistent | ❌ | `conflict_detected` → human |

## Semantic Validation — Computational Check

Tool_use solves syntax problems. But semantic problems require **active validation logic**.

### The calculated_total Field

```json
{
  "line_items": [
    {"description": "Product A", "unit_price": 100, "quantity": 3, "line_total": 300},
    {"description": "Product B", "unit_price": 150, "quantity": 2, "line_total": 300}
  ],
  "stated_total": 650,
  "calculated_total": 600,
  "totals_match": false
}
```

Add the `calculated_total` field to the schema — the model fills it by summing every line. Then in the backend you check `stated_total == calculated_total`. Mismatch → retry or flag. (Compute the sum *yourself* in the backend as well — the model's `calculated_total` may be wrong too; two independent calculations check each other.)

### The conflict_detected Boolean

When a contradiction is detected in the source document:

```json
{
  "vendor_name": "ABC Ltd.",
  "invoice_date": "2024-01-15",
  "stated_total": 1100,
  "calculated_total": 950,
  "conflict_detected": true,
  "conflict_details": "Line total ($950) does not match the cover page total ($1,100)"
}
```

With this flag the system can automatically route to human review. `conflict_detected` (closed value) + `conflict_details` (explanation) — the same **"closed value + explanation" pattern** as `"other"` + the detail field in Task 4.3.

## The detected_pattern Field — Long-Term Improvement

This field can come up as a surprise on the exam.

### What Is It Used For?

For code review agents: recording which code construct triggered each finding.

```json
{
  "finding_id": "BUG-001",
  "severity": "critical",
  "description": "SQL injection risk",
  "detected_pattern": "Direct SQL query inside an f-string: f\"SELECT * FROM {table}\"",
  "dismissed_by_developer": false
}
```

### Why Does It Matter?

Developers dismiss some findings. Thanks to `detected_pattern`:
- Which patterns were dismissed frequently?
- Are the dismissed patterns actually wrong, or is it a prompt calibration problem?
- Which category should be focused on to improve the prompt?

**Systematic data → Systematic improvement.** The loop closes like this:

```
detected_pattern data: the "f-string SQL" pattern is dismissed 70% of the time
   → Investigate: most of the dismissed ones are constant queries in test files
   → Task 4.1: clarify the criterion ("constant queries in the test directory → skip")
   → Task 4.2: add a few-shot example showing that pattern as "acceptable"
   → Task 4.1 eval set: re-measure the false positive rate
```

`detected_pattern` (4.4) and `confidence_reason` (4.6) are Domain 4's *feedback* fields; both loop back to 4.1/4.2.

## Self-Correction Flow — Full Example

A single flow with tool_use, Pydantic validation, error messages, 2 retries, and an "external document" branch (the solution to Preparation Exercise 3, steps 11–12):

```python
import anthropic
from datetime import datetime
from pydantic import BaseModel, ValidationError, model_validator

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"

# --- 1. Tool schema (Task 4.3) ---
EXTRACT_TOOL = {
    "name": "extract_invoice_data",
    "description": "Extract structured data from an invoice document",
    "strict": True,
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            "invoice_date": {"type": ["string", "null"], "description": "YYYY-MM-DD; null if absent"},
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "line_total": {"type": ["number", "null"]},
                    },
                    "required": ["description", "line_total"],
                    "additionalProperties": False,
                },
            },
            "stated_total": {"type": ["number", "null"]},
            "calculated_total": {"type": ["number", "null"]},
            "conflict_detected": {"type": "boolean"},
            "conflict_details": {"type": ["string", "null"]},
            "references_external_document": {"type": ["string", "null"],
                "description": "If the document references another document (contract no. etc.), write it here"},
        },
        "required": ["invoice_number", "invoice_date", "line_items", "stated_total",
                     "calculated_total", "conflict_detected", "conflict_details",
                     "references_external_document"],
        "additionalProperties": False,
    },
}

# --- 2. Validation: schema/type + semantic rules in one place (Pydantic) ---
class LineItem(BaseModel):
    description: str
    line_total: float | None

class Invoice(BaseModel):
    invoice_number: str
    invoice_date: str | None
    line_items: list[LineItem]
    stated_total: float | None
    calculated_total: float | None
    conflict_detected: bool
    conflict_details: str | None
    references_external_document: str | None

    @model_validator(mode="after")
    def semantic_checks(self):
        if self.invoice_date:
            try:
                datetime.strptime(self.invoice_date, "%Y-%m-%d")
            except ValueError:
                raise ValueError(f"invoice_date '{self.invoice_date}' is not in YYYY-MM-DD format")
        totals = [i.line_total for i in self.line_items if i.line_total is not None]
        if totals and self.stated_total is not None:
            backend_sum = sum(totals)               # independent calculation
            if abs(backend_sum - self.stated_total) > 0.01 and not self.conflict_detected:
                raise ValueError(
                    f"Total mismatch: lines {backend_sum}, stated_total {self.stated_total}. "
                    "Either a line/total was misread (fix it) or the document is contradictory "
                    "(set conflict_detected=true and fill in conflict_details)."
                )
        return self

# --- 3. Call + retry loop ---
def extract_with_retry(document: str, max_retries: int = 2) -> dict:
    messages = [{"role": "user", "content": f"Extract data from the invoice below.\n\n<document>\n{document}\n</document>"}]

    for attempt in range(max_retries + 1):
        response = client.messages.create(
            model=MODEL,
            max_tokens=2000,
            tools=[EXTRACT_TOOL],
            tool_choice={"type": "tool", "name": "extract_invoice_data"},  # exam: forced tool
            messages=messages,
        )
        tool_block = next(b for b in response.content if b.type == "tool_use")
        extraction = tool_block.input

        try:
            invoice = Invoice.model_validate(extraction)
        except ValidationError as e:
            errors = "\n".join(f"- {err['loc']}: {err['msg']}" for err in e.errors())
        else:
            # Valid — but separate out the cases retry cannot solve
            if invoice.conflict_detected:
                return {"status": "human_review", "reason": invoice.conflict_details, "data": extraction}
            if invoice.references_external_document and invoice.stated_total is None:
                return {"status": "needs_document", "document": invoice.references_external_document,
                        "data": extraction}          # not a retry: add the missing document, then call again
            return {"status": "ok", "data": extraction}

        if attempt == max_retries:
            break

        # Retry: tool_use block + tool_result containing the error, in the same conversation
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": [{
            "type": "tool_result",
            "tool_use_id": tool_block.id,
            "is_error": True,
            "content": (
                "The extraction did not pass validation. Look at the original document again and "
                f"call the tool again, correcting only the errors below:\n{errors}"
            ),
        }]})

    return {"status": "human_review", "reason": f"Still invalid after {max_retries} retries:\n{errors}",
            "data": extraction}
```

The flow has three exits and the exam wants you to distinguish all three: **`ok`** (retry solved it, or it was correct the first time), **`needs_document`** (not a retry, context), **`human_review`** (the document is contradictory or the retry budget ran out).

---

## Retry Count Limit

```
Recommended: maximum 2-3 retries

The main reason — DIAGNOSIS:
- Retry only solves "the information is in the document" errors (format, field, count)
- If it still fails after 2-3 retries, the error is not in this class:
  information absent / in an external document / document contradictory → more retries will not solve it
- The limit is the point where the decision "this document is not retry's job" is made

Secondary reason — COST:
- Every retry = an extra call + latency
- An infinite loop consumes resources

After the final failed attempt: 
- Add to the human review queue
- Mark with conflict_detected: true
- Alert the downstream system
```

## Key Takeaway List

| # | Key Takeaway |
|---|---------------|
| 1 | **A specific error message is essential in a retry** — "try again" is not enough. Document + failed extraction + error, all three together (via `tool_result` in tool_use). |
| 2 | **Format error, structural error, wrong field → retry is effective.** Schema-syntax errors are already eliminated by tool_use; retry is for semantic errors. |
| 3 | **If the information is not in the source, retry is not effective** — a nullable field is needed. **If the information is in an external document** → add the document, then retry. |
| 4 | **Contradictory source document → conflict_detected flag**, human review. |
| 5 | **calculated_total** is added to the schema for semantic validation; the backend cross-checks with its own calculation. |
| 6 | **detected_pattern** keeps a record of findings → dismissed patterns loop back to the 4.1 criterion / 4.2 example. |
| 7 | **Max 2-3 retries** — the limit is for diagnosis ("this error is not in retry's class"); then the human queue. |

## Practice Questions and Answer Explanations

### Question 1

An invoice extraction system returns null for the `payment_terms` field. A retry message was sent: "payment_terms is a required field, cannot be null." Still null. At the bottom of the invoice it says *"For payment terms see Framework Agreement 2024-17"*. What is the correct conclusion?

**A)** Use a stronger model  
**B)** Make the `payment_terms` field nullable — the information is not in the document  
**C)** Add the framework agreement to the context and re-run the extraction; retry only works once the information is in the context  
**D)** Give the model a few-shot example about payment terms  

**✅ Answer: C**

*Explanation:* The information *exists* but is **in an external document** — the exam guide's "information exists only in an external document not provided" scenario. Retry looks at the same document, null again. (B) would be correct if the document made no reference at all; here the information is reachable, skipping it is data loss. (A) and (D) expect the model to find information it does not have.

### Question 2

An invoice document shows $800 as the line items total, and the cover page says the total is $950. How should the system handle this situation?

**A)** Accept the line total as correct, use $800  
**B)** Accept the cover page total as correct, use $950  
**C)** Mark with conflict_detected: true, route to human review  
**D)** Take the average: use $875  

**✅ Answer: C**

*Explanation:* Contradictory source data — retry does not help, the model cannot determine which value is correct. Flagging with `conflict_detected: true` and routing to human review is the only safe option.

### Question 3

What is the `detected_pattern` field for in a code review agent?

**A)** It records which code construct triggered the finding; it enables analyzing dismissed-finding patterns and improving the prompt  
**B)** It is internal state information the model uses for debugging  
**C)** It shows which validation error occurred in the retry loop  
**D)** It is the alert code sent to the CI/CD system  

**✅ Answer: A**

*Explanation:* `detected_pattern` collects systematic data. When the patterns developers frequently dismiss are analyzed, it becomes visible which categories are poorly calibrated. With this data, prompt criteria (4.1) and few-shot examples (4.2) are improved.

### Question 4

How many retries are recommended for a validation-retry loop? And what should be done after the final failed attempt?

**A)** 1 retry — any error goes to human review  
**B)** 2-3 retries; if it fails, add to the human review queue  
**C)** 10+ retries — the model produces the correct answer over time  
**D)** The retry count should be unlimited — the system keeps trying until it succeeds  

**✅ Answer: B**

*Explanation:* 2-3 retries are sufficient for the error class retry can solve (format/field/count); if it still fails afterwards, the problem is not in this class (information absent, external document, contradictory document) — human review is needed. An infinite loop both masks this and consumes resources.

### Question 5

An extraction system switched to `strict: true` tool_use; schema errors went to zero. The team says "we no longer need the validation-retry loop". Is that correct?

**A)** Yes — strict guarantees schema compliance, validation is unnecessary  
**B)** No — strict only removes schema/syntax errors; validation and retry are still needed for semantic errors such as total mismatches and placement in the wrong field  
**C)** No — in strict mode retry is even more important because the model makes more mistakes  
**D)** Yes — few-shot is sufficient for semantic errors  

**✅ Answer: B**

*Explanation:* The exam guide's distinction: schema syntax errors (eliminated by tool use) vs semantic validation errors (not eliminated). Strict *narrows the scope* of retry — now only semantic errors remain — but does not remove it. (C) strict does not increase the error rate. (D) few-shot provides consistency, it does not guarantee computational correctness.
