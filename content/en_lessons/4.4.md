## The Core Idea

The first extraction isn't always perfect. Validation-retry asks the question: **"Can the error be sent back and can the model correct itself?"**

The answer depends on the situation. And the exam tests exactly whether you know that distinction.

---

## The Retry-with-Error-Feedback Architecture

### Basic Flow

```
1. Document sent → first extraction received
2. Extraction validated
3. If there's an error → sent back to the model with the error message
4. The model sees the original document + the failed extraction + the error
5. The model corrects itself → new extraction
6. Validate again
```

### Contents of the Retry Request

```python
retry_prompt = f"""
Original document:
{original_document}

Your first extraction attempt:
{failed_extraction}

Validation error:
{validation_error}

Please correct the extraction taking the error into account.
"""
```

**Critical:** telling the model just "try again" isn't enough. A **specific error message** is required — the model can't fix what it doesn't know it got wrong.

## Cases Where Retry Is Effective

Memorise these — the exam asks "does retry work for this scenario?"

### ✅ Effective: Format Mismatches

```
Error: "invoice_date is in '15/01/2024' format, expected: 'YYYY-MM-DD'"
Fix: the model returns "2024-01-15".

Why it works: the information IS in the document, just wrongly formatted.
```

### ✅ Effective: Structural Output Errors

```
Error: "the line_items array has 3 items but the total line count says 2"
Fix: the model corrects the line count to 3.

Why it works: the contradiction is detectable; the model can look again and fix it.
```

### ✅ Effective: Wrong Field Placement

```
Error: "the unit_price field shows the total value (450, 3 × 150)"
Fix: the model corrects unit_price to 150 and total to 450.

Why it works: both values are in the source document, only the fields were mixed up.
```

---

## Cases Where Retry Is NOT Effective — The Exam's Trap

### ❌ Not Effective: The Information Really Isn't in the Source

```
Error: "discount_rate null — required field"
Reality: the document never states a discount rate.

What the model does: even retrying, it looks at the same document.
If the information isn't there, the model invents or returns null again.

Right fix: make discount_rate nullable in the schema.
```

### ❌ Not Effective: Inconsistent Source Document

```
Document contents:
- Line items: 300 + 450 + 200 = 950
- Cover page total: 1,100

Retry error message: "Line items sum to 950, stated total 1,100"

What the model does: which is correct? The document contradicts itself.
Retry doesn't help — the model can't choose for the document.

Right fix: add a conflict_detected flag, route to human review.
```

## Semantic Validation — Computational Checks

Tool_use fixes syntax problems. But semantic problems need **active validation logic**.

### The calculated_total Field

```json
{
  "line_items": [
    {"description": "Product A", "unit_price": 100, "quantity": 3, "line_total": 300},
    {"description": "Product B", "unit_price": 150, "quantity": 2, "line_total": 300}
  ],
  "stated_total": 650,
  "calculated_total": 600,
  "totals_match": false
}
```

Add a `calculated_total` field to the schema — the model fills it by summing each line. Then in the backend you check `stated_total == calculated_total`. Mismatch → retry or flag.

### The conflict_detected Boolean

When a contradiction is detected in the source document:

```json
{
  "vendor_name": "ABC Ltd.",
  "invoice_date": "2024-01-15",
  "stated_total": 1100,
  "calculated_total": 950,
  "conflict_detected": true,
  "conflict_details": "Line total (950) does not match the cover page total (1,100)"
}
```

With this flag the system can automatically route to human review.

## The detected_pattern Field — Long-Term Improvement

This field can be a surprise on the exam.

### What Is It For?

For code review agents: recording which code construct triggered each finding.

```json
{
  "finding_id": "BUG-001",
  "severity": "critical",
  "description": "SQL injection risk",
  "detected_pattern": "Direct SQL query in an f-string: f\"SELECT * FROM {table}\"",
  "dismissed_by_developer": false
}
```

### Why It Matters

Developers dismiss some findings. Thanks to `detected_pattern`:
- Which patterns were dismissed frequently?
- Are the dismissed patterns really wrong, or is it a prompt calibration problem?
- Which category should prompt improvement focus on?

**Systematic data → systematic improvement.**

## Self-Correction Flow — Full Example

```python
import anthropic
import json

client = anthropic.Anthropic()

def extract_with_retry(document: str, max_retries: int = 2) -> dict:
    extraction = initial_extract(document)

    for attempt in range(max_retries):
        errors = validate(extraction)

        if not errors:
            return extraction  # Success

        # Retry with error feedback
        extraction = retry_extract(document, extraction, errors)

    # Final check
    final_errors = validate(extraction)
    if final_errors:
        return {"extraction": extraction, "warnings": final_errors}

    return extraction

def validate(extraction: dict) -> list[str]:
    errors = []

    # Format check
    if extraction.get("invoice_date"):
        try:
            datetime.strptime(extraction["invoice_date"], "%Y-%m-%d")
        except ValueError:
            errors.append(f"invoice_date format wrong: '{extraction['invoice_date']}'. Expected: YYYY-MM-DD")

    # Semantic check
    if extraction.get("line_items") and extraction.get("stated_total"):
        calculated = sum(item.get("line_total", 0) for item in extraction["line_items"])
        stated = extraction["stated_total"]
        if abs(calculated - stated) > 1:  # 1 cent tolerance
            errors.append(
                f"Total mismatch: calculated {calculated}, stated {stated}"
            )

    return errors

def retry_extract(document: str, failed: dict, errors: list[str]) -> dict:
    error_text = "\n".join(f"- {e}" for e in errors)

    response = client.messages.create(
        model="claude-opus-4-5",
        max_tokens=1000,
        messages=[{
            "role": "user",
            "content": f"""Original document:
{document}

First extraction:
{json.dumps(failed, ensure_ascii=False, indent=2)}

Validation errors:
{error_text}

Redo the extraction, correcting these errors."""
        }]
    )
    return json.loads(response.content[0].text)
```

## The Retry Count Limit

```
Recommended: maximum 2–3 retries
Why:
- Every retry = extra cost + latency
- If still failing after 3 retries the problem is usually in the source
- An infinite retry loop consumes system resources

After the last failed attempt:
- Add to the human review queue
- Mark with conflict_detected: true
- Warn the downstream system
```

## Key Takeaways

| # | Key takeaway |
|---|---|
| 1 | **A specific error message is essential in the retry** — "try again" isn't enough. |
| 2 | **Format error, structural error, wrong field → retry is effective.** |
| 3 | **If the information isn't in the source, retry isn't effective** — a nullable field is needed. |
| 4 | **Contradictory source document → conflict_detected flag**, human review. |
| 5 | **calculated_total** is added to the schema for semantic validation. |
| 6 | **detected_pattern** records findings for long-term prompt improvement. |
| 7 | **Max 2–3 retries** — then the human queue. No infinite loops. |

## Practice Questions with Explanations

### Question 1

The invoice extraction system returns null for the `payment_terms` field. A retry message was sent: "payment_terms is a required field, cannot be null." Still null. What is the right conclusion?

**A)** Use a stronger model
**B)** Increase the retry count (5–10 attempts)
**C)** Make the `payment_terms` field nullable/optional — the information probably isn't in the document
**D)** Give the model an example about payment terms

**✅ Answer: C**

*Explanation:* the model keeps looking at the same document. If the information isn't there, retry doesn't help. The right fix: make the field nullable in the schema — so the model can return null instead of inventing a plausible value.

### Question 2

The invoice document shows 800 as the sum of line items, and the cover page says the total is 950. How should the system handle this?

**A)** Accept the line total as correct, use 800
**B)** Accept the cover page total as correct, use 950
**C)** Mark with conflict_detected: true, route to human review
**D)** Take the average: use 875

**✅ Answer: C**

*Explanation:* contradictory source data — retry doesn't help; the model can't determine which value is correct. Flagging with `conflict_detected: true` and routing to human review is the only safe option.

### Question 3

What does the `detected_pattern` field do in a code review agent?

**A)** Records which code construct triggered the finding; enables analysing dismissed-finding patterns and improving the prompt
**B)** It's internal state information the model uses for debugging
**C)** It shows which validation error occurred in the retry loop
**D)** It's the alert code sent to the CI/CD system

**✅ Answer: A**

*Explanation:* `detected_pattern` collects systematic data. Analysing the patterns developers frequently dismiss reveals which categories are badly calibrated. That data improves the prompt criteria.

### Question 4

How many retries are recommended for a validation-retry loop? And what should happen after the last failed attempt?

**A)** 1 retry — any error goes to human review
**B)** 2–3 retries; if it fails, add to the human review queue
**C)** 10+ retries — the model eventually produces the right answer
**D)** Unlimited retries — the system tries until it succeeds

**✅ Answer: B**

*Explanation:* 2–3 retries is optimal for cost-benefit. Documents still failing after 3 retries usually have source problems or a completely unknown format — human review is needed. An infinite loop consumes system resources.
