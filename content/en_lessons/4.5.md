## The Core Idea

Not every Claude call has to be synchronous. The **Message Batches API** offers significant cost savings for certain tasks — but it has constraints, and those constraints are the exam's focus.

The basic question: **"Can this workflow tolerate waiting?"**

---

## The Message Batches API — Key Properties

| Property | Value |
|---|---|
| **Cost saving** | 50% (compared with the synchronous API) |
| **Processing window** | Up to 24 hours |
| **Latency guarantee** | None (no defined SLA) |
| **Multi-turn tool calling** | Not supported |
| **Request-response matching** | Via `custom_id` |

---

## Synchronous vs Batch — The Decision Rule

This distinction always appears on the exam. Memorise it:

### Use the Synchronous API (Blocking workflows)

```
- Pre-merge code reviews → developers are waiting for the commit
- Real-time security scanning → the CI/CD pipeline status is awaited
- User-interactive tasks → a human is waiting for the result
- Anything needing an SLA → a latency guarantee is required
```

**Rule:** if a human or a system is waiting for the result → synchronous.

### Use the Batch API (Latency-tolerant workflows)

```
- Overnight reports → ready by morning is enough
- Weekly code quality audits → can wait until the next day
- Overnight test generation → ready in the daytime pipeline
- Large archive analysis → not urgent
- Bulk document extraction → completing within hours is enough
```

**Rule:** if there's a defined latency tolerance and the 50% saving is attractive → batch.

---

## The Exam's Trap

The exam typically presents this scenario:

> *"An engineering manager proposes moving all Claude calls to the Batch API to cut costs."*

**Wrong answers:**
- "Great idea, 50% saving makes a big difference" — no
- "The Batch API is suitable for all tasks" — no

**Right answer:**
> *"Pre-merge checks and tasks the CI/CD pipeline waits on must stay synchronous. Only latency-tolerant workflows (overnight reports, weekly audits) can move to batch."*

**Core principle:** batch doesn't replace synchronous. It only complements it.

## custom_id — Request/Response Matching

In batch processing you track which response belongs to which request with `custom_id`:

```python
import anthropic

client = anthropic.Anthropic()

# Build the batch request
requests = []
for doc_id, document in documents.items():
    requests.append({
        "custom_id": f"doc-{doc_id}",  # Unique ID for tracking
        "params": {
            "model": "claude-opus-4-5",
            "max_tokens": 1000,
            "messages": [{
                "role": "user",
                "content": f"Analyse this document:\n{document}"
            }]
        }
    })

# Submit the batch
batch = client.beta.messages.batches.create(requests=requests)

# Get the results (up to 24 hours)
for result in client.beta.messages.batches.results(batch.id):
    doc_id = result.custom_id  # Which document?

    if result.result.type == "succeeded":
        response = result.result.message.content[0].text
        process_result(doc_id, response)
    else:
        # Failed → resubmit via custom_id
        handle_failure(doc_id, result.result.error)
```

## Handling Failed Requests

Some documents in a batch can fail (too large, bad format, etc.).

### The Right Approach

```
1. Get all batch results
2. Filter the failures via custom_id
3. Resubmit only the failed documents:
   - Oversized documents → split into chunks, resubmit
   - Prompt error → fix the prompt, resubmit
4. Don't resubmit the successful ones — cost doubles
```

```python
failed_requests = []
for result in batch_results:
    if result.result.type != "succeeded":
        original_doc = documents[result.custom_id]

        if "too large" in str(result.result.error):
            # Chunk the document
            chunks = chunk_document(original_doc)
            for i, chunk in enumerate(chunks):
                failed_requests.append({
                    "custom_id": f"{result.custom_id}-chunk-{i}",
                    "params": build_params(chunk)
                })
        else:
            failed_requests.append(rebuild_request(result.custom_id))

# Resubmit only the failures
if failed_requests:
    retry_batch = client.beta.messages.batches.create(requests=failed_requests)
```

## Optimising Before the Batch

**Test on a small sample before submitting a large batch.**

```
Why?
- You submitted a 1,000-document batch, the prompt was wrong
- 24 hours later all results are unusable
- Cost: half is gone, the work starts from scratch

The right approach:
1. Pick 10–20 representative documents
2. Test with the synchronous API
3. Verify extraction quality
4. Fix the problems
5. Move to batch → maximise the first-time success rate
```

## The Multi-Turn Tool Calling Constraint

The exam's trick question:

> *"I want to run an extraction pipeline requiring multi-step tool calls on the Batch API."*

**Answer:** the Batch API doesn't support it. Multi-turn tool calling requires the synchronous API — each tool call result forms the input for the next request.

```
Supported → Batch:
  One request → one response (no tool call, or a single tool call)

Not supported → Batch:
  Request → tool call → tool result → continue → result
  (multi-turn, iterative tool use)
```

## Practical Decision Tree

```
What is the task?
│
├─ Are developers/a system waiting for the result?
│   ├─ YES → Synchronous API
│   └─ NO ↓
│
├─ Is there a defined latency SLA?
│   ├─ YES → Synchronous API
│   └─ NO ↓
│
├─ Is multi-turn tool calling required?
│   ├─ YES → Synchronous API
│   └─ NO ↓
│
└─ Is cost important and latency tolerated?
    ├─ YES → Batch API (50% saving)
    └─ NO → Synchronous API
```

## Key Takeaways

| # | Key takeaway |
|---|---|
| 1 | **Batch API: 50% cost saving, up to 24 hours processing, no SLA.** |
| 2 | **Blocking workflows (CI/CD, pre-merge) → always synchronous.** |
| 3 | **Latency-tolerant workflows (overnight reports, weekly audits) → batch.** |
| 4 | **Request-response matching is done via `custom_id`.** |
| 5 | **Batch does not support multi-turn tool calling.** |
| 6 | **On failures, only the failed documents are resubmitted, not the whole batch.** |

## Practice Questions with Explanations

### Question 1

A team plans to move all Claude calls to the Batch API for a 50% cost saving. This includes: (a) overnight code quality reports, (b) a pre-merge security scan on PRs. Is this plan correct?

**A)** Yes, both uses are suitable for batch
**B)** No, both uses must stay synchronous
**C)** No; the overnight reports can go to batch, the PR security scan must stay synchronous
**D)** Yes, but the Batch API only runs between 00:00 and 06:00

**✅ Answer: C**

*Explanation:* overnight reports are latency-tolerant — ready by morning is enough, batch is suitable. The PR security scan is a blocking workflow — developers wait for the result before merging, synchronous is required. Moving everything to batch breaks CI/CD.

---

### Question 2

500 documents were submitted via the Batch API. After 24 hours: 480 succeeded, 20 failed. What is the next step?

**A)** Resubmit all 500 documents
**B)** Resubmit only the 20 failed documents, modified if necessary
**C)** Inspect the 20 failed documents by hand and skip them
**D)** Reprocess the whole batch with a smaller model

**✅ Answer: B**

*Explanation:* thanks to custom_id you know which documents failed. Resubmitting only those minimises cost. Resubmitting the whole batch means needless spending on 480 successful documents.

---

### Question 3

In which scenario can the Batch API not be used?

**A)** Weekly analysis of 1,000 invoice documents
**B)** Overnight test-case generation
**C)** Extraction requiring multi-step tool calls (result → new tool call → result)
**D)** Bulk classification of archive documents

**✅ Answer: C**

*Explanation:* the Batch API doesn't support multi-turn tool calling. Each batch request is independent — an iterative flow connecting earlier tool results to the next request requires the synchronous API.

---

### Question 4

What is the best practice before starting a large batch job?

**A)** Use the most powerful model — quality rises automatically
**B)** Test on 10–20 representative documents with the synchronous API before sending all documents
**C)** Send the whole batch first, fix the prompt based on the results and resend
**D)** Send without custom_id — it's processed faster

**✅ Answer: B**

*Explanation:* testing on a small sample catches prompt errors early. Instead of waiting 24 hours to learn that all results are unusable, validating first and then sending the large batch saves both time and money.
