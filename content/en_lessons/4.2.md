## The Core Idea

Few-shot prompting: **showing examples** to Claude instead of giving instructions. Saying "here's how it's done" instead of "do this".

This technique is **the most effective way to solve consistency problems.** Not more detailed instructions. Not confidence thresholds. Not a bigger model. **Examples.**

The exam's questions on this topic ask you: *"When should you use few-shot, and when something else?"* To know the answer, first understand when it works.

---

## When Should You Use Few-Shot?

Three trigger scenarios — memorise them:

### Trigger 1: Inconsistent Formatting

```
Problem: you work with the same data but the output format changes every run.
Sometimes JSON, sometimes a markdown table, sometimes plain text.
You added an instruction: "Always output JSON." Still inconsistent.

Fix: a few-shot example — show an input/output pair in exactly the format you want.
```

### Trigger 2: Inconsistent Decisions in Ambiguous Cases

```
Problem: Claude decides differently in certain cases (is the comment a bug or a
style note?). Sometimes it flags, sometimes it skips.

Fix: show an example of that ambiguous case + explain the reasoning for why one
path was chosen in that case.
```

### Trigger 3: Failing to Extract Existing Information

```
Problem: the information is in the document, but the model can't find it or
returns "null" / "not found".

Fix: an example showing a successful extraction from a document of a similar format.
This teaches the model "in this structure, the information is found this way".
```

---

## How to Build a Good Few-Shot Example

**Rule 1: 2–4 examples are enough.** You don't need 10. 2–4 targeted, well-chosen examples make a dramatic difference.

**Rule 2: Pick ambiguous/hard cases.** Don't exemplify easy cases — it already does those well. Show examples for boundary cases, edge cases, the points where the model hesitates.

**Rule 3: Show the reasoning in every example.** The model generalises from the example — it doesn't just pattern-match. The reasoning lets the model transfer to new, similar cases.

### Structure

```
Example 1:
Input: [hard case A]
Reasoning: [why X was chosen, not Y]
Output: [expected format/decision]

Example 2:
Input: [hard case B — an alternative variant]
Reasoning: [why a different decision this time]
Output: [expected format/decision]
```

## Concrete Example: A Code Review Agent

### Scenario

The agent reviews a comment and must decide "is this a bug or a style preference?"

### ❌ Instruction-Based (Inconsistent)

```
"If the comment describes wrong behaviour, flag it as a bug.
If it only makes a suggestion, skip it."
```

This instruction seems to work, but Claude calibrates the "wrong behaviour" threshold differently every time.

### ✅ Few-Shot (Consistent)

```
Example 1:
Code:
  def calculate_discount(price, rate):
      # rate should be between 0 and 100
      return price * rate  # Actually expects rate in 0-1

Decision: BUG
Reasoning: the comment says 0-100 is expected, the code expects 0-1.
Claimed behaviour contradicts actual behaviour → flag.

---

Example 2:
Code:
  def get_users():
      # Maybe a cache could be added
      return db.query("SELECT * FROM users")

Decision: SKIP
Reasoning: this is a suggestion; it doesn't misdescribe the code's behaviour.
No actual-vs-claimed contradiction → skip.
```

Now when Claude meets new cases it generalises from this reasoning pattern.

## The Hallucination-Reduction Effect

This is especially critical in **document extraction** tasks.

### Problem

You process invoices in various formats:
- Some use inline references: "Item A (Unit price: 50)"
- Some use a table: `| Item | Qty | Price |`
- Some are plain text: "3 items in total, 50 each"

The model extracts fields correctly in some formats, and in others returns "null" or **invents a value** (hallucination).

### Fix: Few-Shot Showing Format Variety

```
Example A (inline format):
Document: "Item A (Unit price: 50, Qty: 3)"
Extraction: {"item": "Item A", "unit_price": 50, "qty": 3}

Example B (table format):
Document: "| Item A | 3 | 50 |"
Extraction: {"item": "Item A", "unit_price": 50, "qty": 3}

Example C (plain text):
Document: "3 x Item A, 50 each"
Extraction: {"item": "Item A", "unit_price": 50, "qty": 3}

Example D (no information):
Document: "Item A shipped."
Extraction: {"item": "Item A", "unit_price": null, "qty": null}
```

**The critical last example:** if the information isn't there, null — don't invent. Without this example the model usually prefers to invent a value.

## Few-Shot vs Other Techniques — Decision Matrix

| Problem | Fix |
|---|---|
| Inconsistent format | Few-shot examples |
| Wrong decisions in ambiguous cases | Few-shot + reasoning |
| Can't find existing information (returns null) | Few-shot, similar format |
| Syntactically invalid JSON output | JSON schema via tool_use |
| Semantic errors (wrong value but valid JSON) | Validation-retry loop |
| High cost, latency-tolerant tasks | Batch API |

The exam assumes you know this table. If you can't match the right technique to each scenario, you lose points.

## The Exam's Trap: The "More Instructions" Trap

The exam gives you this:

> *The model makes inconsistent decisions. You make the instructions more detailed. Still inconsistent. What should you do?*

**Wrong answers:**
- "Write longer, more detailed instructions" — instruction volume isn't the fix
- "Adjust the model's confidence parameter" — you have no such parameter
- "Use a bigger model" — the problem isn't the model's capacity

**Right answer:**
- "Add 2–4 few-shot examples for the problematic cases, showing the reasoning in each"

## Key Takeaways

| # | Key takeaway |
|---|---|
| 1 | **Few-shot is the most effective technique for consistency problems.** Not more instructions. |
| 2 | **2–4 targeted examples are enough.** Pick edge cases, ambiguous cases. |
| 3 | **Show the reasoning in every example.** The model generalises, it doesn't memorise patterns. |
| 4 | **In document extraction, examples showing format variety reduce hallucination.** |
| 5 | **The "null if no information" example is critical** — without it the model invents. |
| 6 | **Inconsistent formatting, ambiguous decisions, empty fields → the three few-shot triggers.** |

## Practice Questions with Explanations

### Question 1

You're building a document extraction pipeline. For some documents the "payment date" field is extracted correctly; for others it returns null — but the date is in the document. Which fix is most effective?

**A)** Add "payment date" as a required field in the schema definition
**B)** Instruct the model "if a date exists you must extract it"
**C)** Add few-shot examples showing different date formats (DD/MM/YYYY, "15 January 2024", "Jan 15")
**D)** Add a retry loop: retry when null is returned

**✅ Answer: C**

*Explanation:* the problem is the model not recognising different date formats. Few-shot examples teach the map "in this format the information is here". A required field (A) leads to fabrication. The instruction (B) was already tried and didn't work. Retry (D) repeats the same failed approach.

---

### Question 2

How many few-shot examples is a code review agent recommended to use?

**A)** 1 — few but effective
**B)** 2–4 — targeted examples
**C)** 10–15 — comprehensive coverage
**D)** 50+ — maximum consistency

**✅ Answer: B**

*Explanation:* 2–4 well-chosen examples give dramatic improvement. More examples fill the context window with diminishing returns. 1 example is insufficient for generalisation. 10+ is rarely needed.

---

### Question 3

What is the purpose of showing reasoning in few-shot examples?

**A)** To slow Claude's thinking process and make it decide more carefully
**B)** To let Claude generalise from the examples to new, similar cases
**C)** To let Claude verify which answer is "correct"
**D)** To shorten the length of the instructions

**✅ Answer: B**

*Explanation:* the reasoning teaches the model not just "in this case do this" but "why you do this". That lets the model correctly classify new cases it has never seen by applying the same reasoning. This is the basis of transferability.

---

### Question 4

In an extraction pipeline the document structures vary widely: tables, plain text, nested lists. What is the best approach to reduce hallucination?

**A)** Define a strict JSON schema — all fields required
**B)** A separate model deployment per format type
**C)** Few-shot examples showing successful extraction from varied document structures + a "null if no information" example
**D)** Raise the safety threshold: tell the model "don't write if unsure"

**✅ Answer: C**

*Explanation:* hallucination usually comes from the model inventing a "plausible" value instead of extracting from the format. Few-shot teaches the model the right extraction strategy. The "null if no information" example teaches returning null instead of inventing. A strict required schema (A) does the opposite — it causes fabrication.
