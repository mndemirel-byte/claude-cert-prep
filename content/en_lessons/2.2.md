## The Core Idea

Tools do not always succeed. Timeouts happen, invalid input arrives, permission is denied. The question is: **when a tool fails, HOW do you tell Claude?**

MCP has the **`isError` flag** for this. When a tool returns an error you set this flag to `true` and add structured error information to the response. That way Claude can understand what went wrong and make the right decision.

---

## The Four Error Categories

Memorise these four — the exam expects you to tell them apart:

### 1. Transient
Timeout, service temporarily unavailable. **Retryable.** Wait a little, try again.

```json
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "Database connection timed out — retry in 5 seconds"
}
```

### 2. Validation
Invalid input — wrong format, missing required field. **Fix the input, retry.**

```json
{
  "isError": true,
  "errorCategory": "validation",
  "isRetryable": true,
  "description": "Customer ID must be numeric — 'abc123' is an invalid format"
}
```

### 3. Business
Policy violation — refund amount exceeds the limit, account suspended. **Not retryable.** A different workflow is needed. Must have `retryable: false` and include a message that can be explained to the customer.

```json
{
  "isError": true,
  "errorCategory": "business",
  "isRetryable": false,
  "description": "Refund amount ($750) exceeds the maximum limit ($500). Manager approval required.",
  "customerMessage": "Your refund request will be forwarded to a manager for review."
}
```

### 4. Permission
Access denied. Requires escalation or different credentials.

```json
{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false,
  "description": "No permission to access this account — admin-level credentials required"
}
```

---

## Structured Error Metadata

A good error response contains:

- **`isError`** — `true` or `false`
- **`errorCategory`** — transient / validation / business / permission
- **`isRetryable`** — boolean — can it be retried?
- **`description`** — human-readable explanation
- **`customerMessage`** (optional) — a message that can be relayed to the customer (especially for business errors)

When Claude sees this structure it knows what to do: retry on transient, fix the input on validation, look for an alternative path on business, start escalation on permission.

## Critical Distinction: Access Failure vs Valid Empty Result (EXAM TRAP)

Learn this distinction cold. The exam tests it.

### Access Failure
The tool **could not reach** the data source — timeout, authentication failure. You don't know whether the data exists. **Retrying makes sense.**

### Valid Empty Result
The tool **successfully** queried the source and found no match. There is no data. **Retrying is WRONG.** The answer is "no results found".

Confusing these two breaks the recovery logic.

### Access Failure Example

```json
{
  "isError": true,
  "errorCategory": "transient",
  "isRetryable": true,
  "description": "Database connection timed out"
}
```

### Valid Empty Result Example — THIS IS NOT AN ERROR

```json
{
  "isError": false,
  "results": [],
  "resultCount": 0,
  "description": "Query succeeded, no matching records found"
}
```

The difference: an empty result has `isError: false` — because the tool ran successfully. The result is simply empty. The agent should not retry; it should tell the customer "no record found".

## Error Propagation in Multi-Agent Systems

How should subagents handle errors?

1. **Recover transient errors locally** — retry themselves
2. Propagate to the coordinator **only errors they cannot resolve locally**
3. When propagating, include:
   - **Partial results** — what they obtained before the failure
   - **What was attempted** — which recovery steps were taken

This lets the coordinator make an informed decision — call the same subagent again, use a different subagent, or route to a human.

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| `isError` flag | The core mechanism for error communication in MCP |
| Four error categories | Transient (retry), Validation (fix input), Business (don't retry, alternative path), Permission (escalate) |
| Structured metadata | errorCategory + isRetryable + description — so Claude decides correctly |
| Business errors | `isRetryable: false` + customer-friendly message — retrying policy violations is WRONG |
| Access failure vs empty result | Access failure → retry. Empty result → don't retry, answer "not found" |
| Error propagation | Subagents recover locally, propagate what they can't resolve with partial results |

## Practice Scenario

> A customer support agent calls the order lookup tool. The tool returns:
>
> ```json
> { "results": [], "status": 200 }
> ```
>
> The agent retries 3 times, then tells the customer "There's a problem with the system, please try again later."
>
> The actual situation: the customer has no order matching that number.
>
> **What is the problem and how is it fixed?**
>
> **A)** The agent's retry logic is insufficient — raise the retry count to 5 and increase the wait time.
>
> **B)** The tool response does not distinguish an access failure from a valid empty result. The agent mistakes the empty array for an error. Fix: mark the successful empty result explicitly by adding `isError: false` and `resultCount: 0` to the tool response.
>
> **C)** Add "do not retry on an empty result" to the agent's system prompt.
>
> **D)** Replace the order lookup tool with a broader tool.

### Correct Answer: B

**Why B is correct:** The problem is that the tool cannot distinguish an access failure from a valid empty result. `status: 200` indicates a successful query, but the agent cannot tell because there is no explicit `isError` flag. Fix: use a structured response format that clearly separates a successful empty result (`isError: false`, `resultCount: 0`) from an access failure (`isError: true`, `errorCategory: transient`). When the agent sees `isError: false` it does not retry and tells the customer "order not found".

**Why A is wrong:** Raising the retry count does not fix it — the problem is not insufficient retries but a successful empty result being mistaken for an error. Even after 5 attempts the result is the same: an empty array. Because the order really does not exist.

**Why C is wrong:** A prompt instruction is probabilistic. The real problem is in the tool's response structure — a structural problem needs a structural fix. A prompt instruction will not work reliably in every case.

**Why D is wrong:** Replacing the tool does not solve it — if the new tool uses the same ambiguous response structure the problem persists. The root cause is the response format, not the tool's scope.
