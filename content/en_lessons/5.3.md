## The Core Idea

In multi-agent systems and data extraction pipelines, errors are inevitable. A tool times out, an API denies access, a data source returns no results. The critical question: **what do you do when an error occurs?**

This task statement teaches how to report errors in a structured way, two common anti-patterns, and the difference between an access failure and a valid empty result.

---

## Structured Error Context

When an error occurs, saying just "an error occurred" isn't enough. The error report should contain four pieces of information:

### 1. Failure Type

Remember from Domain 2 — four categories:

| Type | Description | Action |
|---|---|---|
| **Transient** | Network timeout, temporary service outage | Consider retry |
| **Validation** | Invalid parameter, format error | Fix the parameters |
| **Business** | Business-logic rejection (e.g. insufficient balance) | Alternative approach |
| **Permission** | Access denied | Escalation or permission request |

### 2. What Was Attempted

The specific query and the parameters used:

```json
{
  "attempted_action": "journal_search",
  "query": "geothermal energy capacity 2023-2024",
  "parameters": {
    "database": "ScienceDirect",
    "date_range": "2023-01-01 to 2024-12-31",
    "filters": ["peer-reviewed"]
  }
}
```

### 3. Partial Results

Data collected before the error:

```json
{
  "partial_results": {
    "sources_completed": ["IEA", "IRENA", "BloombergNEF"],
    "sources_failed": ["ScienceDirect"],
    "findings_so_far": [
      {"claim": "Solar capacity grew 45%", "source": "IEA"}
    ]
  }
}
```

### 4. Potential Alternative Approaches

```json
{
  "alternatives": [
    "Try alternative database: Google Scholar",
    "Use cached version from last sync",
    "Proceed with partial results and annotate gap"
  ]
}
```

## Two Anti-Patterns — EXAM CRITICAL

On the exam these two anti-patterns constantly appear as **wrong answer options**:

### Anti-Pattern 1: Silent Suppression

Returning empty results marked as "successful".

```json
// WRONG — silent suppression
{
  "status": "success",
  "results": [],
  "error": null
}
```

**Why dangerous:** the upper layer doesn't know there was an error. The recovery mechanism can't kick in. The report is written on incomplete data but nobody knows about the gap.

### Anti-Pattern 2: Workflow Termination

Killing the whole pipeline because of a single error.

```
Source 3/5 unreachable → CANCEL THE WHOLE RESEARCH
```

**Why dangerous:** 4 sources were processed successfully — this throws those partial results away. All the work is lost because of a single failure.

### The Right Approach

```json
{
  "status": "partial_success",
  "completed_sources": 4,
  "failed_sources": 1,
  "findings": [...],
  "errors": [
    {
      "source": "ScienceDirect",
      "failure_type": "transient",
      "attempted": "journal_search for geothermal data",
      "suggestion": "retry or use alternative source"
    }
  ],
  "coverage_note": "Geothermal section limited due to ScienceDirect timeout"
}
```

## Access Failure vs Valid Empty Result — EXAM TRAP

This distinction is tested very subtly. Confusing the two leads to serious mistakes:

### Access Failure

The tool **couldn't reach** the data source:

- Network timeout
- Invalid API key
- Service down

→ **Retry can be considered.** The data may be there, but we couldn't reach it.

### Valid Empty Result

The tool **reached** the data source and **found no** matching results:

- No records in the database for this date range
- No customer matches the search criteria
- This product isn't in inventory

→ **Retry is UNNECESSARY.** The data source was reached successfully and the answer is "no results". That **is the answer itself**. Retrying gives the same result.

### Decision Table

| Situation | Did the tool reach the source? | Result | Action |
|---|---|---|---|
| Access failure | ❌ No | Unknown | Consider retry |
| Valid empty result | ✅ Yes | No match | Don't retry — this IS the answer |

## Coverage Annotations

### Problem

A synthesis report should cover 5 energy sources. But the geothermal data source couldn't be reached. The report silently skips the geothermal section.

When the reader reads the report they can't tell whether geothermal was deliberately excluded or the data was missing.

### Fix

In the synthesis output state which findings are well supported and which areas have gaps:

```
## Research Coverage
- Solar energy: ✅ Comprehensive (3 sources)
- Wind energy: ✅ Comprehensive (2 sources)
- Hydroelectric: ✅ Comprehensive (2 sources)
- Biomass: ✅ Partial (1 source)
- Geothermal: ⚠️ Limited — data missing due to ScienceDirect access timeout
```

**Rule:** explicit coverage annotation instead of silent omission. "The geothermal section is limited due to an unreachable journal source" is always better than silent omission.

---

## Key Exam Takeaways

| Concept | Remember |
|---|---|
| Structured error context | Failure type + what was attempted + partial results + alternatives |
| Silent suppression | ❌ Presenting an empty result as success — recovery is blocked |
| Workflow termination | ❌ Killing the whole pipeline for one error — partial results are lost |
| Access failure | The source couldn't be reached → consider retry |
| Valid empty result | The source was reached, no match → retry UNNECESSARY, this is the answer |
| Coverage annotations | State which areas are well supported and which have gaps |

## Practice Scenario 1

> A multi-agent research system collects data from 5 academic sources. 4 sources returned results successfully. The 5th (ScienceDirect) gave a network timeout error.
>
> The agent's current behaviour: after the timeout it cancels the whole research and returns a "research could not be completed" message.
>
> **What is the right approach?**
>
> **A)** Cancelling the whole research is correct — a report shouldn't be written on incomplete data.
>
> **B)** Continue with the results from the 4 sources, report the failed source with structured error information and add a coverage annotation to the synthesis output.
>
> **C)** Silently ignore the ScienceDirect error and write the report with 4 sources — the user won't notice the difference.
>
> **D)** Retry all 5 sources in an infinite loop — eventually they all work.

### Correct Answer: B

**Why B is correct:** avoids the workflow termination anti-pattern. Preserves the partial results of the 4 successful sources, reports the failed source with structured error information and adds a coverage annotation to the synthesis output. The reader knows which sections are limited.

**Why A is wrong:** the workflow termination anti-pattern. Throws away the results of 4 successful sources because of a single failure.

**Why C is wrong:** the silent suppression anti-pattern. The error is silently swallowed, nobody knows about the gap, the recovery mechanism can't kick in.

**Why D is wrong:** infinite retry locks the system. The assumption that transient errors "eventually resolve" isn't always true. After a reasonable number of retries, continue with partial results.

## Practice Scenario 2

> A customer support agent searches for the customer's order. The tool returns:
>
> ```json
> {
>   "status": "success",
>   "results": [],
>   "message": "No orders found matching criteria"
> }
> ```
>
> The agent interprets this as "order not found, let's try again" and runs the same query 3 more times.
>
> **What is the problem with this behaviour?**
>
> **A)** The agent should raise the retry count — 3 isn't enough, try 10.
>
> **B)** The agent is confusing a valid empty result with an access failure. Status is "success" — the tool reached the source and found no match. That is the answer itself. Retry is unnecessary.
>
> **C)** The tool is malfunctioning — it should always return results.
>
> **D)** The agent should retry with different parameters — not the same ones.

### Correct Answer: B

**Why B is correct:** status "success" means the tool reached the source successfully. Empty result = no match. This isn't an access failure but a valid empty result. Retrying gives the same result — needless resource consumption.

**Why A is wrong:** more retries return the same valid empty result. The problem isn't the retry count but the interpretation of the result.

**Why C is wrong:** the tool is working correctly. "No match" is a valid answer — a tool isn't obliged to always return a non-empty result.

**Why D is wrong:** the search was done with the information the customer gave and there's no result. Changing the parameters (e.g. searching a different name) can lead to wrong results. Ask the customer for additional information first.
